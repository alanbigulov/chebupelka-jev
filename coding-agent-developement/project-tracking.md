# Учёт задач chebu

Тексты задач хранятся в репозитории, в каталоге [tickets/](tickets/README.md). Статус, отметки критериев и доказательства ведутся в трекере. Трекером ученика служит снимок сессии в `.handoff/`, и GitHub для него не нужен. GitHub Issues и Project подключаются по желанию как адаптер. Учебный roadmap объясняет смысл задач и ссылается на тикеты.

Владелец исходного репозитория ведёт GitHub-адаптер: [chebu — Разработка и обучение](https://github.com/users/alanbigulov/projects/4). Репозиторий: https://github.com/alanbigulov/chebupelka-jev.

## Где находится источник данных

| Данные | Источник |
|---|---|
| Текст задачи, критерии, исходная база, источники | Файл тикета в [tickets/](tickets/README.md) |
| Статус, отметки критериев, доказательства | Трекер: раздел «Тикет и трекер» снимка `.handoff/` либо issue и карточка Project |
| Учебный смысл, место изменения и исторические решения | [development-roadmap.md](development-roadmap.md) |
| История изменения структуры | [project-structure.md](project-structure.md) |
| Передача текущей локальной сессии | Состояние `.handoff/`: `SESSION.md` и архив, вне Git |

## Статусы и переходы

| Статус | Когда использовать |
|---|---|
| Бэклог | Идея записана, исполнение ещё не согласовано или не начато |
| К выполнению | Согласованы конкретный объём и критерии следующего шага |
| В работе | Агент или человек действительно выполняет задачу |
| Проверка | Изменение готово, результат и критерии ещё проверяются |
| Заблокировано | Записаны конкретное препятствие, ответственное действие и условие снятия |
| Готово | Согласованные критерии проверены и доказательства записаны |

```text
Бэклог -> К выполнению -> В работе -> Проверка -> Готово
                                |         |
                                +---------+--> Заблокировано
                                                  |
                                  после устранения +--> предыдущий этап
```

Существование тикета не разрешает автоматически реализовать его. Перед началом согласуй с учеником минимальный план. Не отмечай «В работе» задачу, к которой никто не приступил. Отсутствие текста модели, завершение программы или успешный импорт сами по себе не доказывают достижение критериев задачи.

Частичное выполнение отражается отметками критериев, и тикет остаётся открытым. EDU-06 уже имеет две проверенные части, но остальные сценарии пока не реализованы.

## Трекер в снимке сессии

Раздел «Тикет и трекер» [шаблона снимка](../.handoff/TEMPLATE.md) содержит таблицу прогресса: тикет, статус, отмеченные критерии и доказательство. Агент переносит таблицу из прежнего снимка в новый и меняет только строки, по которым шла работа. Статус меняется перед реальной работой. Тикет получает «Готово» после проверки каждого критерия.

Снимок хранится только на машине ученика. Чтобы прогресс пережил удаление клона, перенеси `SESSION.md` и `archive/` приватно либо подключи GitHub-адаптер в своём fork.

## GitHub-адаптер

Адаптер повторяет тикеты в issues и показывает их на Kanban-доске. Подразделы ниже описывают адаптер владельца исходного репозитория. Ученик, которому нужен такой же, создаёт в своём fork issues из файлов тикетов и свой Project с полем Status.

С адаптером статус и отметки критериев ведутся в issue и карточке Project, а снимок хранит их URL и наблюдаемые значения. Расхождение между файлом тикета и issue владельца показывает проверка:

```bash
python3 coding-agent-developement/tickets/issues_sync.py
```

### Представления одного проекта

| Представление | Что показывает |
|---|---|
| [Общая доска](https://github.com/users/alanbigulov/projects/4/views/1) | Все задачи кода, обучения и выпуска |
| [Код агента](https://github.com/users/alanbigulov/projects/4/views/2) | Issues с меткой area:agent |
| [Учебные материалы](https://github.com/users/alanbigulov/projects/4/views/3) | Issues с меткой area:learning |

Это три Board-представления одной очереди, а не копии тикетов. Поле колонок каждого представления: `Status`. Перемещение карточки меняет Status этого же project item. Горизонтальная дополнительная группировка не настроена.

```text
GitHub Issue / ticket
      |
      v
Один item в Project
      |
      +--> Общая доска
      +--> Код агента: label area:agent
      `--> Учебные материалы: label area:learning
```

### Issue и карточка

| Данные | Источник в адаптере |
|---|---|
| Обсуждение, отметки критериев, проверенные результаты | GitHub Issue |
| Этап выполнения | Поле Status в Project |
| Целевая версия | Milestone issue, отображаемый в Project |
| Приоритет и рекомендуемая последовательность | Поля Приоритет и Порядок в Project |
| Область и тип задачи | Labels issue |

Issue является тикетом. Не создавай отдельный draft item для уже существующего issue. Для продолжения задачи используй её номер и стабильный ID EDU; перед созданием новой ищи совпадения в открытых и закрытых issues.

Частичное выполнение в адаптере отмечается чек-листом и меткой `status:partial`; issue остаётся открытым. После завершения всей задачи удали метку частичности.

Закрытие issue и Status проекта являются разными состояниями. После закрытия явно проверь колонку Готово. При повторном открытии верни карточку на подходящий этап. Не полагайся на автоматические workflow без проверки их результата.

### Метки, поля и версии

| Метка | Назначение |
|---|---|
| area:agent | Код агента, его инструменты и проверки |
| area:learning | Уроки, упражнения, паспорта версий |
| area:organization | Приёмка и публикация выпусков |
| type:bug | Исправление поведения |
| type:feature | Новая возможность |
| type:testing | Проверки поведения |
| type:documentation | Учебные и справочные документы |
| type:release | Приёмка выпуска |
| status:partial | Проверена только часть критериев |

Приоритет имеет варианты Высокий, Средний, Низкий. Порядок является числом и задаёт рекомендуемую последовательность; он не является дедлайном и не означает автоматическое начало работы. В интерфейсе при необходимости выбери сортировку по Порядок.

На карточках всех трёх досок отображаются название, исполнитель, labels, milestone, Приоритет и Порядок. Status задаёт колонку. Конфигурация и значения полей проверены через GitHub API; визуальный просмотр браузером в этой сессии не выполнялся.

### Шаблон нового issue

```markdown
## Контекст и учебная тема
Что наблюдается сейчас, где находится код, какая версия является исходной базой.

## Цель и границы
Одна проверяемая задача. Что требуется согласовать до изменения.

## Критерии готовности
- [ ] Наблюдаемый результат.
- [ ] Необходимые проверки.
- [ ] Учебное объяснение и ссылки, если задача меняет изучаемый код.

## Связанные задачи
ID/URL зависимостей, учебного тикета и приёмки выпуска.

## Источники
Ссылки на исходники конкретной версии, уроки и решения.

## Запись завершения
Коммит/PR, команды и результаты проверок, непроверенные сценарии, принятое решение.
```

Добавь одну область, тип и milestone; затем добавь существующий issue в Project и заполни Status, Приоритет и Порядок. Секреты, локальные логи с личными данными и состояние `.handoff/` не публикуются.

В репозитории два remote, и команда `gh` без ключа `-R` может обратиться к `upstream`. Называй репозиторий явно, например `gh issue view 6 -R alanbigulov/chebupelka-jev`.

## Работа в каждой сессии

1. Начни сессию по [AGENTS.md](../AGENTS.md): команда `start`, снимок, перепроверка Git и трекера.
2. Выбери с учеником конкретный тикет, прочитай его файл и согласуй объём.
3. Перед реальной работой обнови статус в трекере и записывай существенные решения и результаты.
4. Выполни проверки, запиши доказательства и ограничения. Закрывай тикет только при выполнении согласованных критериев.
5. Сверь состояние трекера с фактическим результатом. При изменении учебного смысла обнови roadmap и уроки.
6. Заверши сессию снимком по [протоколу](../.handoff/README.md). Снимок содержит ссылки и наблюдения, а не копию документации.

[Протокол](../.handoff/README.md), шаблон и скрипт передачи хранятся в Git и одинаковы для всех рантаймов. Снимок `.handoff/SESSION.md` и архив исключены из Git и не появляются после нового клонирования; для другой машины их переносят приватно.
