## 2. Почему мы добавили `upstream`

`origin` и `upstream` являются именами удалённых адресов внутри локальных настроек Git. Это соглашение об именовании. `origin` у нас указывает на собственный GitHub, а `upstream` на исходный проект автора.

```text
Один локальный репозиторий .git
    |
    +-- origin   --> alanbigulov/chebupelka-jev
    |
    +-- upstream --> alexey-goloburdin/chebupelka
```

Мы выполнили:

```bash
git remote add upstream https://github.com/alexey-goloburdin/chebupelka.git
git fetch upstream
```

| Команда | Что она сделала |
|---|---|
| `git remote add upstream ...` | Сохранила дополнительный адрес в настройках локального Git |
| `git fetch upstream` | Загрузила объекты истории автора и обновила ссылку `upstream/main` |

`fetch` не объединяет истории, не меняет текущую локальную ветку и не выкладывает файлы автора в рабочую папку. Сначала он делает их доступными для просмотра из локального Git.

Подтверждение из вывода:

```text
From https://github.com/alexey-goloburdin/chebupelka
 * [new branch]      main       -> upstream/main
```

## 3. Как мы посмотрели две истории

После загрузки были выполнены команды только для чтения:

```bash
git remote -v
git log --oneline --graph --all --decorate
git ls-tree --name-only upstream/main
```

Удалённые адреса:

```text
origin    https://github.com/alanbigulov/chebupelka-jev.git (fetch)
origin    https://github.com/alanbigulov/chebupelka-jev.git (push)
upstream  https://github.com/alexey-goloburdin/chebupelka.git (fetch)
upstream  https://github.com/alexey-goloburdin/chebupelka.git (push)
```

`(push)` означает, что Git знает адрес для отправки. Эта строка не подтверждает отправку и не даёт права менять репозиторий автора. Во время сессии мы отправляли изменения только в `origin`.

Граф до объединения:

```text
* 14be2c6 (HEAD -> main, origin/main) first commit
* 59da137 (upstream/main, upstream/HEAD) youtube link
* ff1e9ac youtube link
* a796a0c init
```

Этот компактный вывод содержит две независимые истории. Их можно представить отдельно:

```text
Собственная история:
14be2c6                       <-- main, origin/main, HEAD

История автора:
a796a0c --> ff1e9ac --> 59da137 <-- upstream/main
```

| Обозначение | Как его читать |
|---|---|
| `HEAD -> main` | Сейчас выбрана локальная ветка `main` |
| `main` | Указатель на последний коммит локальной ветки |
| `origin/main` | Последнее известное локальному Git состояние ветки на собственном GitHub |
| `upstream/main` | Последнее полученное состояние ветки автора |
| `upstream/HEAD` | Подсказка о ветке по умолчанию у автора |

`origin/main` является локальной ссылкой. Чтобы узнать новые изменения на сервере, требуется получить их через `fetch`; после успешного собственного `push` Git также обновляет известное ему состояние этой ветки.

Список файлов автора:

```text
.gitignore
.python-version
README.md
chebupelka.py
pyproject.toml
uv.lock
```

`git ls-tree` показывает дерево выбранного коммита. Так можно изучить файлы другой ветки без переключения рабочей директории.

## 4. Объединение независимых историй

Перед объединением мы проверили отсутствие незаписанных изменений:

```bash
git status
```

Результат:

```text
On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean
```

После этого:

```bash
git merge upstream/main --allow-unrelated-histories --no-commit
```

| Часть команды | Значение |
|---|---|
| `merge upstream/main` | Подготовить объединение ветки автора с текущей веткой |
| `--allow-unrelated-histories` | Разрешить объединение без общего начального коммита |
| `--no-commit` | Остановиться перед созданием коммита для проверки результата |

В независимых историях оба репозитория создали `README.md`. Git не смог сам выбрать, какое содержимое сохранить:

```text
Auto-merging README.md
CONFLICT (add/add): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
```

`add/add` означает, что файл с одинаковым именем добавлен в обеих историях. Это ожидаемая остановка объединения, при которой остальные файлы уже подготовлены.

```text
Changes to be committed:
        new file:   .gitignore
        new file:   .python-version
        new file:   chebupelka.py
        new file:   pyproject.toml
        new file:   uv.lock

Unmerged paths:
        both added: README.md
```

Здесь полезно различать три состояния:

```text
Рабочие файлы --> git add --> Индекс --> git commit --> История Git
                               |
                               +-- содержит подготовленный результат объединения
```

Индекс, который также называют staging area, хранит содержимое будущего коммита. Во время конфликта Git ждёт, пока мы запишем в него выбранный результат.

## 5. Как мы разрешили конфликт README

Мы выбрали README автора с описанием проекта и командами запуска:

```bash
git restore --source=upstream/main --worktree README.md
git add README.md
```

Первая команда взяла файл из `upstream/main` и заменила его в рабочей директории. Вторая подготовила выбранную версию и отметила конфликт разрешённым.

`git add` применяют также при разрешении конфликтов. Первоначальный README собственного репозитория сохранился в первом коммите `14be2c6`.

Проверки:

```bash
git status
git diff --cached --stat
```

Git сообщил:

```text
All conflicts fixed but you are still merging.
  (use "git commit" to conclude merge)
```

Статистика подготовленных файлов завершалась так:

```text
6 files changed, 371 insertions(+), 1 deletion(-)
```

`--cached` просматривает подготовленные изменения в индексе. Обычный `git diff` показывает ещё не подготовленные изменения относительно индекса.

Пока объединение не завершено коммитом, команда `git merge --abort` позволяет отменить его. В нашей сессии исходная рабочая директория была чистой, и отмена не понадобилась.

## 8. Почему терминал запускал старый `uv`

Проверили происхождение инструментов:

```bash
command -v uv
command -v python3
brew list --versions uv
```

Получили:

```text
/Users/alanbigulov/.local/bin/uv
/Users/alanbigulov/miniconda3/bin/python3
uv 0.12.14
```

На машине были два экземпляра `uv`. Оболочка находила старую версию в `~/.local/bin`, а Homebrew уже содержал новую.

```text
Команда uv
    |
    v
Поиск по PATH слева направо
    |
    +-- ~/.local/bin/uv      найден первым, версия 0.5.15
    |
    +-- Homebrew/bin/uv      версия 0.12.14, обычная команда до неё не дошла
```

`PATH` является списком каталогов, в которых оболочка ищет исполняемые программы. `command -v` показывает, какой путь она выбирает.

Новый экземпляр проверили напрямую:

```bash
"$(brew --prefix)/bin/uv" --version
```

Результат:

```text
uv 0.12.14 (Homebrew 2026-09-15 aarch64-apple-darwin)
```

`$(brew --prefix)` подставляет корневой каталог Homebrew. Кавычки сохраняют итоговый путь одним аргументом команды. Такой запуск выбирает нужный бинарный файл без изменения `PATH` и без удаления старого `uv`.

Во время сессии мы не обновляли старый экземпляр и не меняли Conda `base`. Python, доступный по обычной команде `python3`, продолжал зависеть от окружения терминала.

## 9. Создание отдельного окружения проекта

Использовали проверенный Homebrew-экземпляр:

```bash
"$(brew --prefix)/bin/uv" sync
```

Вывод:

```text
Using CPython 3.14.7
Creating virtual environment at: .venv
Resolved 6 packages in 845ms
Prepared 4 packages in 289ms
Installed 5 packages in 11ms
 + certifi==2026.5.20
 + charset-normalizer==3.4.7
 + idna==3.18
 + requests==2.34.2
 + urllib3==2.7.0
```

Вывод подтверждает выбор CPython 3.14.7 и создание `.venv`. Он не содержит сообщения о скачивании самого интерпретатора, поэтому по нему нельзя заключить, что Python впервые установлен именно этой командой. `uv` умеет выбирать уже доступный Python и при необходимости получать управляемый интерпретатор.

```text
.python-version ----+
                    |
pyproject.toml -----+--> uv sync --> .venv/
                    |                 |
uv.lock ------------+                 +-- Python 3.14.7
                                      +-- requests и зависимости

Conda base ------------------------------ остаётся отдельным окружением
```

`requests` использует дополнительные библиотеки. Поэтому пять установленных пакетов не означают пять прямых зависимостей нашего агента. В разрешённый набор также входит запись самого локального проекта, обозначенная в lock-файле как `virtual`.

Для запуска через `uv run` ручная активация `.venv` не требуется. Даже при видимом `(base)` команда `uv run` выбирает окружение проекта.

Проверки:

```bash
"$(brew --prefix)/bin/uv" run python --version
"$(brew --prefix)/bin/uv" run python -c "import requests; print(requests.__version__)"
git status --short
```

Результаты:

```text
Python 3.14.7
2.34.2
 M uv.lock
```

`.venv` не появилась в статусе, потому что [`.gitignore`](../../.gitignore) исключает её из Git. В репозитории сохраняют требования и lock-файл, а окружение воспроизводят на каждой машине.

## 11. Настройка облачного API DeepSeek

Для первого запуска выбран облачный провайдер DeepSeek и API формата OpenAI Chat Completions с вызовом инструментов.

| Параметр | Значение нашей конфигурации |
|---|---|
| Провайдер | DeepSeek |
| Название модели, указанное при выборе | DeepSeek-V4.1-Flash |
| Идентификатор в запросе | `deepseek-flash` |
| Базовый адрес | `https://api.deepseek.com` |
| Конечный адрес POST-запроса | `https://api.deepseek.com/chat/completions` |
| Переменная с ключом | `DEEPSEEK_API_KEY` |
| Режим рассуждений | Явно выключен через `thinking` |

В историческом `chebupelka.py` заменили заглушки и добавили `os`:

```python
import os

LLM_BASE_URL = "https://api.deepseek.com"
LLM_API_KEY = os.environ["DEEPSEEK_API_KEY"]
LLM_MODEL = "deepseek-flash"
```

Это же содержимое находится в [настройках текущего файла](../../chebupelkajev.py). Ключ не записан в код. `os.environ` читает переменные процесса, а квадратные скобки требуют присутствия нужной переменной. Если её нет, Python выбрасывает `KeyError` при загрузке модуля.

В `call_llm()` добавили параметр:

```python
"thinking": {"type": "disabled"},
```

В этой версии код сохраняет `content` и `tool_calls`, но не сохраняет `reasoning_content`. Режим рассуждений отключили, чтобы не добавлять обработку этого поля в первый учебный запуск. Поддержка такого режима остаётся темой будущего развития. Документация провайдера может меняться; закреплённый результат сессии состоит в успешном запуске данной конфигурации.

Проверяли правки командой:

```bash
git --no-pager diff -- chebupelka.py
```

Обычный `git diff` открыл просмотрщик. Показанное внизу `:` относилось к нему, а не к ошибке Python. В просмотрщике `Space` листает дальше, `q` завершает просмотр. `--no-pager` выводит diff сразу в терминал.

## 12. Как ввели ключ без записи в код

В терминале `zsh` выполнили:

```zsh
read -rs "DEEPSEEK_API_KEY?Вставь ключ DeepSeek и нажми Enter: "
printf '\n'
export DEEPSEEK_API_KEY
```

| Команда | Результат |
|---|---|
| `read -rs ...` | Считывает введённое значение без отображения символов |
| `printf '\n'` | Переводит вывод на следующую строку |
| `export DEEPSEEK_API_KEY` | Передаёт переменную дочерним процессам, в том числе Python |

Секрет вводится в ответ на приглашение `read`. Он не является частью команды, которую оболочка записывает в историю. В новой независимой сессии терминала значение потребуется ввести заново.

В v0.1.0 нет чтения `.env`. Создание такого файла само по себе не передаст ключ программе. Ключ также доступен дочерним процессам агента, поскольку команды наследуют его окружение. Отдельное ограничение окружения инструментов запланировано в [roadmap](../development-roadmap.md).

## 13. Первый тест проверил только API

Сначала сделали один короткий запрос без запуска `agent_loop()` и без выполнения команд. Историческая команда:

```bash
"$(brew --prefix)/bin/uv" run python - <<'PY'
import requests
from chebupelka import LLM_BASE_URL, LLM_MODEL, LLM_HEADERS

response = requests.post(
    f"{LLM_BASE_URL}/chat/completions",
    headers=LLM_HEADERS,
    json={
        "model": LLM_MODEL,
        "messages": [{"role": "user", "content": "Ответь одним словом: подключено"}],
        "thinking": {"type": "disabled"},
        "max_tokens": 32,
    },
    timeout=60,
)

print("HTTP:", response.status_code)
response.raise_for_status()
print("Ответ:", response.json()["choices"][0]["message"]["content"])
PY
```

После переименования строка импорта для повторения теста должна быть такой:

```python
from chebupelkajev import LLM_BASE_URL, LLM_MODEL, LLM_HEADERS
```

`python -` читает программу со стандартного ввода. Конструкция `<<'PY'` передаёт многострочный код до отдельной строки `PY`. Кавычки вокруг маркера не дают оболочке подставлять переменные внутрь Python-кода.

Наблюдаемый ответ:

```text
HTTP: 200
Ответ: Да
```

Модель ответила `Да`, хотя запрос просил слово `подключено`. Для проверки подключения важны успешный HTTP-статус и полученное сообщение. Этот тест подтвердил работу адреса, авторизации, модели и разбора ответа. Выполнение инструментов он ещё не проверял.

`timeout=60` присутствует в этом тестовом фрагменте. В функции `call_llm()` агента v0.1.0 HTTP-таймаут пока не задан. Эти два случая следует различать.

Импорт выполнил настройки модуля, включая чтение ключа, но не запустил нижний блок `if __name__ == "__main__"`. Подробно это объяснено в [уроке 3](03-code-walkthrough.md).

## 14. Второй тест проверил полный цикл агента

Исторический запуск:

```bash
"$(brew --prefix)/bin/uv" run python chebupelka.py \
  "Вызови инструмент bash ровно один раз с командой pwd. Затем сообщи текущую директорию и заверши работу. Файлы не изменяй."
```

Тот же запуск с именем v0.1.0:

```bash
"$(brew --prefix)/bin/uv" run python chebupelkajev.py \
  "Вызови инструмент bash ровно один раз с командой pwd. Затем сообщи текущую директорию и заверши работу. Файлы не изменяй."
```

Полученный в сессии вывод:

```text
============================================================
🔄 Turn 1
============================================================
🔧 Tool: bash({"command": "pwd"})
   → Exit code: 0
/Users/alanbigulov/Projects/chebupelka-jev

============================================================
🔄 Turn 2
============================================================

🤖 Текущая директория: `/Users/alanbigulov/Projects/chebupelka-jev`

Инструмент `bash` вызван ровно один раз с командой `pwd`; файлы не изменялись.

✅ Agent finished
```

`pwd` печатает рабочую директорию процесса. Модель выбрала эту команду, Python запустил её, а результат был отправлен обратно модели.

```text
Ход 1: задача --> DeepSeek --> запрос bash("pwd")
                                  |
                                  v
                             subprocess.run
                                  |
                                  v
                        путь и код завершения 0
                                  |
                                  v
Ход 2: вся история --> DeepSeek --> текстовый ответ --> return
```

| Что проверено | Доказательство |
|---|---|
| Модель умеет запросить инструмент | `Tool: bash({"command": "pwd"})` |
| Локальная команда выполнилась | `Exit code: 0` и путь папки |
| Результат вернулся модели | Во втором ходе модель назвала полученную директорию |
| Цикл завершился | `Agent finished` |

Проверено два обращения к модели и один вызов инструмента. По этому тесту нельзя утверждать, что проверены несколько одновременных вызовов, длительные задачи или обработка ошибок. API-запросы требуют доступа к провайдеру и могут тарифицироваться; повторение теста создаст новые запросы.

## 16. Что фиксирует версия v0.1.0

После проверенного запуска мы разобрали код и согласовали выпуск собственной учебной версии. Переименование и документы входят в v0.1.0; исправления поведения агента намечены на следующие версии.

| Элемент | Состояние v0.1.0 |
|---|---|
| Имя исходного файла | `chebupelkajev.py` |
| Имя Python-проекта | `chebupelkajev` |
| Версия проекта | `0.1.0` в `pyproject.toml` и записи проекта в `uv.lock` |
| Git-тег | `v0.1.0`, закрепляет коммит выпуска |
| Собственный GitHub | `alanbigulov/chebupelka-jev`, адрес сохранён |
| Источник | `alexey-goloburdin/chebupelka`, ссылка и история сохранены |
| Учебные материалы | Эта папка `lessons-v0.1.0` |
| План продолжения | [development-roadmap.md](../development-roadmap.md) |
| Документы процесса | [VERSIONING.md](../../VERSIONING.md), [CHANGELOG.md](../../CHANGELOG.md) |

Для `VERSIONING.md` и `CHANGELOG.md` по выбранному решению установлен бит исполнения `+x`. Эти файлы остаются Markdown-документами. Бит исполнения сам по себе не превращает их текст в shell-скрипт; записанные в них команды выполняют отдельно.

Тег выпуска публикуется отдельно от ветки. Подробные команды и проверки находятся в [VERSIONING.md](../../VERSIONING.md). Исторические идентификаторы первых коммитов сохраняются:

2091f34  объединение с тремя коммитами автора
   |
2dd92ca  согласование имени проекта в uv.lock
   |
55fa8de  подключение DeepSeek через переменную окружения
   |
коммит выпуска v0.1.0: имя chebupelkajev и учебная документация
