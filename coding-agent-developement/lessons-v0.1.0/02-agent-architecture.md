# Урок 2. Архитектура агента chebupelkajev v0.1.0

Агент состоит из одного Python-файла и четырёх функций. Модель выбирает ответ или команду, Python выполняет команду локально, затем отправляет её результат модели вместе с предыдущими сообщениями.

```text
                            Сеть
Терминал                     |                  Компьютер пользователя
    |                        |                             |
    v                        |                             v
Текст задачи                 |                        Рабочие файлы
    |                        |                             ^
    v                        |                             |
agent_loop() --> call_llm() --+--> DeepSeek API              |
    ^               ^        |       |                     |
    |               |        |       v                     |
    |          вся история <--+-- текст / tool_calls         |
    |                             |                        |
    +-- результат <-- call_tool() <-- запрос bash           |
                          |                                |
                          v                                |
                      run_bash() --> /bin/sh --> команда ---+
```

Схема показывает связи, а не отдельные фоновые процессы Python. Функции вызываются последовательно в одном процессе агента. Команда инструмента запускается как дочерний процесс.

## 2. Кто за что отвечает

Основные определения находятся в [исходном файле](https://github.com/alanbigulov/chebupelka-jev/blob/f6108317f85553eb6acdec7dc94fe13ba115b367/chebupelkajev.py):

| Часть | Строка начала v0.1.0 | Ответственность | Возвращаемые данные |
|---|---:|---|---|
| Настройки и описания | 7 | Адрес, модель, ключ, инструкция и схема инструмента | Константы модуля |
| `run_bash()` | 39 | Запуск команды через оболочку | Строка с кодом завершения и выводом |
| `call_tool()` | 48 | Выбор Python-функции по имени инструмента | Строка результата или ошибки |
| `call_llm()` | 58 | Запрос к модели и извлечение ответа | Пара `content`, `tool_calls` |
| `agent_loop()` | 76 | История сообщений, ходы и завершение | Полезного возвращаемого значения нет |
| Блок `__main__` | 102 | Получение задачи из терминала | Вызов основного цикла |

Порядок определений в файле помогает Python знать о функциях до запуска. Порядок выполнения для пользователя начинается с нижнего блока:

```text
if __name__ == "__main__"
          |
          v
     agent_loop()
          |
          +--> call_llm() --> HTTP --> DeepSeek
          |
          +--> call_tool() --> run_bash() --> команда
          |
          `--> печать ответа и return
```

`call_llm()` не выполняет локальные команды. `run_bash()` не обращается к модели. `agent_loop()` соединяет эти действия через переменные и список сообщений.

## 3. Что является состоянием агента

Главное состояние находится в локальной переменной `messages` внутри `agent_loop()`:

```python
messages: list[dict[str, object]] = [
    {"role": "system", "content": SYSTEM_PROMPT},
    {"role": "user", "content": user_message},
]
```

Здесь код развёрнут на несколько строк для чтения. Содержимое совпадает с началом функции в версии v0.1.0.

| Состояние | Время жизни |
|---|---|
| `messages` | Пока выполняется один вызов `agent_loop()` |
| `turn` | Номер хода текущего запуска |
| `content`, `tool_calls` | Ответ последнего обращения к модели |
| `result` | Результат последнего инструмента, затем копируется в историю |
| Настройки `LLM_*` | После загрузки модуля и до завершения процесса |

Новый запуск создаёт новый список сообщений. История не записывается в файл и не восстанавливается после завершения. Вывод терминала помогает человеку наблюдать ход работы, но программа не читает его обратно как память.

На каждом ходе агент повторно отправляет всю историю. API получает контекст в поле `messages`; код не использует серверный идентификатор сохраняемой беседы.

## 4. Четыре роли сообщений

В этой версии используются роли `system`, `user`, `assistant` и `tool`:

```text
system     --> как агент должен действовать
user       --> что пользователь просит сделать
assistant  --> какой инструмент запросила модель
tool       --> что вернуло локальное выполнение
```

| Роль | Кто создаёт содержимое | Пример |
|---|---|---|
| `system` | Разработчик в `SYSTEM_PROMPT` | Используй `bash`, заверши обычным ответом |
| `user` | Пользователь через аргументы терминала | Выполни `pwd` один раз |
| `assistant` | Модель, а Python сохраняет её запрос | Вызвать `bash` с `command="pwd"` |
| `tool` | Python после выполнения команды | `Exit code: 0` и путь директории |

В `SYSTEM_PROMPT` описан порядок действий с планированием. Отдельного планировщика в коде нет. Это текстовая инструкция модели. Код не проверяет, что модель объяснила действие, построила план или действительно решила исходную задачу.

Обычный финальный ответ печатается и завершает функцию. В v0.1.0 он не добавляется в `messages`, поскольку дальнейшего хода уже нет.

## 5. Как описание инструмента попадает к модели

В [`LLM_TOOLS`, строки 26–36](https://github.com/alanbigulov/chebupelka-jev/blob/f6108317f85553eb6acdec7dc94fe13ba115b367/chebupelkajev.py#L26) описан один инструмент:

```json
{
  "type": "function",
  "function": {
    "name": "bash",
    "description": "Execute a shell command and return the output.",
    "parameters": {
      "type": "object",
      "properties": {
        "command": {
          "type": "string",
          "description": "The bash command to execute."
        }
      },
      "required": ["command"]
    }
  }
}
```

Это JSON-совместимое описание имени и аргументов. По нему модель формирует запрос инструмента. Исполняемую функцию `run_bash` мы на сервер не отправляем.

```text
LLM_TOOLS --> модель узнаёт имя bash и аргумент command
                        |
                        v
                 tool_calls из ответа
                        |
                        v
call_tool() --> локальное соответствие "bash": run_bash
```

Описание схемы и реальная функция должны согласовываться. В этой версии схема требует `command`, а `run_bash(command: str)` принимает этот параметр. Подсказки типов Python и схема для модели не заменяют локальную проверку внешнего ответа. Такая проверка намечена в `EDU-03` в [roadmap](../development-roadmap.md).

## 6. Как устроен обмен с DeepSeek

[`call_llm()`, строки 58–73](https://github.com/alanbigulov/chebupelka-jev/blob/f6108317f85553eb6acdec7dc94fe13ba115b367/chebupelkajev.py#L58), создаёт `payload`, отправляет POST-запрос, проверяет HTTP-статус и возвращает две части ответа.

```text
Python-словарь payload
         |
         v
requests.post(json=payload, headers=LLM_HEADERS)
         |
         v
JSON по HTTPS --> /chat/completions
         |
         v
HTTP-ответ --> raise_for_status() --> .json()
         |
         v
choices[0].message --> content, tool_calls
```

Ключ передаётся в HTTP-заголовке `Authorization: Bearer ...`. В теле запроса находятся модель, история сообщений, описание инструмента и параметры генерации.

| Поле запроса | Значение v0.1.0 | Следствие |
|---|---|---|
| `model` | `deepseek-flash` | Используется выбранный идентификатор API |
| `messages` | Весь текущий список | Модель получает предыдущие действия и вывод |
| `tools` | `LLM_TOOLS` | Модель знает доступный инструмент |
| `tool_choice` | `auto` | Может ответить текстом или запросить инструмент |
| `thinking` | `{"type": "disabled"}` | Этот запуск не требует сохранения `reasoning_content` |
| `temperature` | `0.1` | Настройка вариативности, не гарантия повторяемости |
| `max_tokens` | `4096` | Лимит длины ответа одного обращения |

`max_tokens` не ограничивает всю стоимость запуска и не уменьшает входную историю. Использование токенов и стоимость программа пока не показывает.

## 7. Почему аргументы инструмента разбираются ещё раз

HTTP-ответ уже превратился в структуры Python через `.json()`. Но значение `function.arguments` внутри него по протоколу является строкой с JSON:

```python
tool_call = {
    "id": "example_call_id",
    "type": "function",
    "function": {
        "name": "bash",
        "arguments": '{"command": "pwd"}',
    },
}
```

`example_call_id` здесь учебное значение; реальный идентификатор API в сессии не печатался.

```text
HTTP JSON
   |
   +--> response.json() --> словарь tool_call
                                   |
                                   +--> arguments, ещё строка JSON
                                                |
                                                v
                                           json.loads()
                                                |
                                                v
                                       {"command": "pwd"}
```

Полученный словарь распаковывается в аргументы Python-функции через `func(**arguments)`.

## 8. Выполнение команды и границы процесса

[`run_bash()`, строки 39–45](https://github.com/alanbigulov/chebupelka-jev/blob/f6108317f85553eb6acdec7dc94fe13ba115b367/chebupelkajev.py#L39), вызывает:

```python
subprocess.run(
    command,
    shell=True,
    capture_output=True,
    text=True,
    timeout=120,
)
```

Параметры показаны на отдельных строках; в исходнике вызов записан одной строкой.

Имя инструмента `bash` условное. При `shell=True` на macOS и других POSIX-системах Python по умолчанию использует `/bin/sh`, если не указан другой `executable`. Поэтому выполнение команд с особенностями именно Bash не гарантировано.

Команда наследует рабочую директорию Python-процесса и окружение. В тесте агент запущен из папки репозитория, поэтому `pwd` вернул её путь. Параметры `cwd` и `env` в вызове не заданы.

```text
Python-процесс агента
   |
   +-- текущая директория: chebupelka-jev/
   +-- окружение: включает DEEPSEEK_API_KEY
   |
   `-- дочерняя оболочка /bin/sh
           |
           `-- команда из ответа модели
```

`.venv` изолирует Python-библиотеки. Она не ограничивает доступ shell-команд к файлам компьютера. У инструмента пока нет подтверждения пользователя, изолированной рабочей области или ограниченного окружения. Эти изменения описаны в `EDU-04` и `EDU-05` в [roadmap](../development-roadmap.md).

## 9. Как команда возвращает результат

`subprocess.run()` возвращает объект с `stdout`, `stderr` и `returncode`. `run_bash()` собирает из них строку:

```text
Exit code: 0
/Users/alanbigulov/Projects/chebupelka-jev
```

Если `stderr` непустой, добавляется отдельная подпись `STDERR:`. Код `0` обычно означает успех. Ненулевой код означает состояние, определённое самой командой.

В вызове не задан `check=True`, поэтому ненулевой код сам по себе не выбрасывает исключение Python. Результат с таким кодом возвращается модели. Если превышено время ожидания, `TimeoutExpired` превращается в строку ошибки.

Таймаут 120 секунд относится к вызову `subprocess.run()`. В этой версии не настроено управление всей группой дочерних процессов, поэтому гарантированное завершение дерева процессов отдельно намечено в `EDU-10`.

В терминал выводятся первые 500 символов:

```python
print(f"   → {result[:500]}{'...' if len(result)>500 else ''}")
```

В историю записывается полный `result`. Большой вывод полностью собирается в памяти и отправляется модели на следующем ходе. Ограничение печати не является ограничением входного контекста API.

## 10. Как запрос и результат связываются в истории

Для каждого вызова код добавляет сообщение `assistant`, затем `tool`:

```python
messages.append({
    "role": "assistant",
    "content": content or None,
    "tool_calls": [tool_call],
})
messages.append({
    "role": "tool",
    "tool_call_id": tool_call_id,
    "content": result,
})
```

`tool_call_id` в результате должен совпасть с `id` запроса. Это связывает вывод команды с действием, которое модель попросила выполнить.

История проверенного теста:

```text
Перед ходом 1
  [system, user]
       |
       v
DeepSeek запросил bash("pwd")
       |
       v
Добавлены assistant и tool
  [system, user, assistant(tool_call), tool(result)]
       |
       v
Перед ходом 2 вся история отправлена снова
       |
       v
DeepSeek вернул текст без tool_calls
       |
       v
Печать ответа и завершение
```

## 11. Как программа решает завершиться

У цикла есть два способа нормального выхода по текущей логике:

| Условие | Действие |
|---|---|
| Модель не вернула `tool_calls` | Напечатать текст, если он есть, и выйти через `return` |
| Выполнены все `MAX_TURNS` ходов | Напечатать сообщение об остановке по пределу |

```text
Ответ модели
     |
     +-- content есть --------> печать текста
     |
     v
tool_calls пустой?
     |
     +-- да ------------------> Agent finished --> return
     |
     `-- нет -----------------> команды --> история --> следующий ход
```

Если нет ни текста, ни инструментов, программа печатает `(no text output)` и также завершает цикл. Она не проверяет содержательную успешность задачи по отдельному критерию.

`MAX_TURNS = 1000` ограничивает число обращений к модели через основной цикл. Он не равен числу команд: один ответ может содержать несколько запросов инструмента. Предел высок для учебного запуска, а финансового лимита в коде нет. Управление ходами, выводом и бюджетом включено в `EDU-09`.

## 12. Ограничение при нескольких вызовах инструментов

В текущем коде `messages.append()` находится внутри цикла `for tool_call in tool_calls`. Если модель вернёт сразу вызовы `A` и `B`, программа сохранит:

```text
assistant: tool_calls [A]
tool:      result A
assistant: tool_calls [B]
tool:      result B
```

Исходный ответ модели содержал одно сообщение с обоими вызовами. Чтобы сохранить его без изменения структуры, история должна выглядеть так:

```text
assistant: tool_calls [A, B]
tool:      result A
tool:      result B
```

Одновременные вызовы не проверялись облачным тестом с `pwd`. Различие видно по расположению строк 97–98. Исправление запланировано как `EDU-01`; в v0.1.0 текущее поведение сохранено.

## 13. Где ошибки обрабатываются, а где останавливают запуск

| Ситуация | Поведение v0.1.0 | Где продолжить изучение |
|---|---|---|
| Не задан ключ | `KeyError` при загрузке модуля | `EDU-07` |
| Задача пустая при заданном ключе | Сообщение и `sys.exit(1)` | Нижний блок запуска |
| HTTP вернул ошибку | `raise_for_status()` выбрасывает исключение | `EDU-02` |
| Нет ответа от API | У основного HTTP-запроса нет явного таймаута | `EDU-02` |
| Ответ API имеет неожиданную форму | Обращение через `[...]` может выбросить исключение | `EDU-02`, `EDU-03` |
| Аргументы инструмента не являются корректным JSON | `json.loads()` выбрасывает исключение до `call_tool()` | `EDU-03` |
| Неизвестное имя инструмента | `call_tool()` возвращает строку ошибки | Урок 3 |
| Ошибка при вызове выбранной функции | `call_tool()` превращает исключение в строку | `EDU-03` |
| Команда вернула ненулевой код | Код и вывод отправляются модели | Урок 3 |
| Команда превысила 120 секунд | Возвращается строка о таймауте | `EDU-10` |
| Достигнут предел ходов | Печатается сообщение об остановке | `EDU-09` |

Эти ограничения не исправлены в данном выпуске. Таблица описывает исходники, а не утверждает, что все ошибочные ситуации были воспроизведены в первой сессии. Тесты без платного API запланированы в `EDU-06`.

## 14. Что действительно доказали первые запуски

Проверка HTTP 200 доказала, что выбранные настройки позволили получить ответ от DeepSeek. Тест `pwd` дополнительно подтвердил запрос инструмента, локальное выполнение, передачу результата и завершение после второго ответа модели.

```text
Наблюдалось в облаке
  1 запрос только с текстом --> HTTP 200, ответ "Да"
  2 хода полного агента -----> 1 вызов pwd, код 0, итоговый ответ

Не было проверено этими запусками
  несколько вызовов в одном ответе
  HTTP-ошибки и задержки
  некорректные аргументы
  режим рассуждений
  длительные команды и большие выводы
```

При подготовке выпуска также используются локальные проверки исходников и воспроизведение двух ходов с подменённым HTTP-ответом. Они помогают проверить переименование и структуру цикла без новых запросов к провайдеру. Такой тест не является повторной проверкой облачного API.

## 15. Как связать архитектуру со следующей доработкой

| Часть, которую меняем | Что нужно понимать до изменения |
|---|---|
| История нескольких инструментов | Одно сообщение `assistant` сохраняет весь исходный список вызовов |
| HTTP-обмен | Ошибка сети, HTTP-статус и неверный JSON являются разными событиями |
| Схема аргументов | Данные от модели требуют проверки до выполнения |
| Подтверждение команд | Между выбором модели и `subprocess.run()` нужна отдельная точка решения |
| Изоляция | Рабочая директория и окружение дочернего процесса задаются явно |
| Настройки модели | Изменение режима требует согласования формата истории с API |
| Лимиты | Ходы, токены, длина вывода и время выполнения ограничиваются отдельно |

Рабочие статусы и критерии каждого улучшения ведутся в [development-roadmap.md](../development-roadmap.md). Правила новых тегов находятся в [VERSIONING.md](../../VERSIONING.md).

Для самопроверки найди в [коде v0.1.0](https://github.com/alanbigulov/chebupelka-jev/blob/f6108317f85553eb6acdec7dc94fe13ba115b367/chebupelkajev.py): место отправки истории, место фактического запуска команды и условие завершения. Это три разные точки выполнения, и каждая отвечает за своё действие.
