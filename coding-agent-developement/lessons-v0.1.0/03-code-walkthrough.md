## 1. Что Python делает до входа в `agent_loop()`

Python выполняет верхний уровень файла сверху вниз. Он загружает модули, создаёт настройки, затем определяет функции через `def`. Тела функций начинают выполняться при вызове.

В начале файла:

```python
import json, sys, subprocess
import requests
import os
```

| Импорт | Зачем нужен |
|---|---|
| `json` | Преобразовать JSON-строку аргументов инструмента в Python-объект и обратно для печати |
| `sys` | Получить аргументы запуска через `sys.argv` и завершиться через `sys.exit()` |
| `subprocess` | Запустить локальную команду |
| `requests` | Выполнить запрос к HTTP API |
| `os` | Прочитать переменную окружения с ключом |

Первая строка файла, `"""Minimal coding agent loop …"""`, является строкой документации модуля. Она описывает файл и не запускает агент.

Далее выполняются настройки:

```python
LLM_BASE_URL = "https://api.deepseek.com"
LLM_API_KEY = os.environ["DEEPSEEK_API_KEY"]
LLM_MODEL = "deepseek-flash"
LLM_HEADERS = {
    "Content-Type": "application/json",
    "Authorization": f"Bearer {LLM_API_KEY}",
}
MAX_TURNS = 1000
```

`f"Bearer {LLM_API_KEY}"` является f-строкой. Python подставляет значение переменной в фигурных скобках при создании заголовков.

Ключ читается сразу при загрузке файла. Поэтому отсутствие `DEEPSEEK_API_KEY` вызовет `KeyError` раньше, чем программа дойдёт до проверки задачи. Заголовки также создаются один раз; изменение окружения после импорта не пересоздаст их автоматически.

Инструкция `SYSTEM_PROMPT` и схема `LLM_TOOLS` тоже определяются до входа в цикл. Их роль подробно разобрана в [уроке 2](02-agent-architecture.md).

## 2. Почему нижний блок срабатывает при запуске, но не при импорте

Точка запуска находится в [строках 102–107](https://github.com/alanbigulov/chebupelka-jev/blob/f6108317f85553eb6acdec7dc94fe13ba115b367/chebupelkajev.py#L102):

```python
if __name__ == "__main__":
    prompt = " ".join(sys.argv[1:]) if len(sys.argv) > 1 else ""
    if not prompt.strip():
        print("No task provided. Exiting.")
        sys.exit(1)
    agent_loop(prompt)
```

`__name__` задаётся Python автоматически:

| Действие | Значение внутри этого модуля | Выполнение нижнего блока |
|---|---|---|
| `python chebupelkajev.py "задача"` | `"__main__"` | Условие истинно |
| `import chebupelkajev` | `"chebupelkajev"` | Условие ложно |
| `from chebupelkajev import LLM_MODEL` | `"chebupelkajev"` | Условие ложно |

Импорт выполняет верхний уровень модуля, включая чтение ключа, определения функций и проверку `if`. Но при импорте тело нижнего `if` пропускается. Поэтому первый тест API мог импортировать настройки без запуска цикла агента.

```text
Прямой запуск файла                    Импорт модуля
       |                                    |
       v                                    v
импорты, настройки, def              импорты, настройки, def
       |                                    |
       v                                    v
__name__ == "__main__"? да           __name__ == "__main__"? нет
       |                                    |
       v                                    v
получение задачи и agent_loop()      функции доступны импортирующему коду
```

## 3. Где находятся `sys.argv[0]`, `sys.argv[1:]` и `join()`

В реальном коде на строке 103 есть:

```python
prompt = " ".join(sys.argv[1:]) if len(sys.argv) > 1 else ""
```

`sys.argv[0]` отдельно в этом файле не используется. Оно появилось в обсуждении как объяснение устройства аргументов. `sys.argv[1:]` находится внутри `join()` на строке 103.

Для запуска:

```bash
python chebupelkajev.py "Выполни pwd"
```

список выглядит так:

```python
sys.argv == ["chebupelkajev.py", "Выполни pwd"]
```

| Выражение | Значение в примере |
|---|---|
| `sys.argv[0]` | `"chebupelkajev.py"` |
| `sys.argv[1:]` | `["Выполни pwd"]` |
| `len(sys.argv)` | `2` |
| `" ".join(sys.argv[1:])` | `"Выполни pwd"` |

Индексы списков начинаются с нуля. Срез `[1:]` берёт элементы от индекса 1 до конца, пропуская имя файла. `join()` соединяет строки из списка разделителем. Здесь разделителем является один пробел.

Вся правая часть присваивания является условным выражением:

```text
результат_если_да if условие else результат_если_нет
```

Если есть аргументы после имени файла, они соединяются в задачу. Если аргументов нет, `prompt` становится пустой строкой.

При нескольких отдельных аргументах они тоже соединятся:

```python
argv_example = ["chebupelkajev.py", "Выполни", "pwd"]
prompt_example = " ".join(argv_example[1:])
# prompt_example == "Выполни pwd"
```

Для передачи задачи используем кавычки в терминале. Они удерживают текст одним аргументом и предотвращают интерпретацию многих символов оболочкой. Кавычки, заданные оболочкой для группировки, в сам текст аргумента не попадают.

Номер строки можно найти в рабочем файле:

```bash
rg -n 'sys\.argv' chebupelkajev.py
```

## 4. Как проверяется пустая задача

```python
if not prompt.strip():
    print("No task provided. Exiting.")
    sys.exit(1)
```

`strip()` возвращает строку без пробельных символов по краям. Он не меняет исходную строку `prompt`. В этой проверке временный результат используется только для условия.

| `prompt` | `prompt.strip()` | Результат проверки |
|---|---|---|
| `""` | `""` | Завершение с кодом 1 |
| `"   "` | `""` | Завершение с кодом 1 |
| `"\n\t"` | `""` | Завершение с кодом 1 |
| `" Выполни pwd "` | `"Выполни pwd"` | Вызов агента с исходным `prompt` |

Пустая строка считается ложной в условии Python. `not` меняет логическое значение, поэтому `not ""` истинно.

`sys.exit(1)` прекращает текущий Python-процесс с кодом 1. Код завершения доступен оболочке. Эта проверка выполняется после загрузки настроек, следовательно для неё тоже должен быть доступен ключ.

## 5. Как задача становится параметром функции

В конце блока запуска:

```python
agent_loop(prompt)
```

Начало функции, [строка 76](https://github.com/alanbigulov/chebupelka-jev/blob/f6108317f85553eb6acdec7dc94fe13ba115b367/chebupelkajev.py#L76):

```python
def agent_loop(user_message: str) -> None:
```

| Часть | Значение |
|---|---|
| `def` | Определение функции |
| `agent_loop` | Имя функции |
| `user_message` | Параметр, доступный внутри функции |
| `: str` | Подсказка, что параметр ожидается строкой |
| `-> None` | Подсказка, что полезного возвращаемого значения нет |

При вызове значение `prompt` становится значением `user_message`. Имена могут различаться, потому что переменные принадлежат разным областям видимости.

```text
prompt в блоке запуска
         |
         v
agent_loop(prompt)
         |
         v
user_message внутри функции
```

Подсказки типов не проверяют переданные значения автоматически. Они помогают человеку и инструментам анализа. Функция печатает результат в терминал, а не возвращает его вызывающему коду.

## 6. Как создаётся история

```python
messages: list[dict[str, object]] = [
    {"role": "system", "content": SYSTEM_PROMPT},
    {"role": "user", "content": user_message},
]
```

Здесь используются список и словари:

| Запись | Что означает |
|---|---|
| `[ ... ]` | Список элементов в заданном порядке |
| `{ ... }` | Словарь с ключами и значениями |
| `"role"` | Строковый ключ словаря |
| `"system"` | Значение роли первого сообщения |
| `SYSTEM_PROMPT` | Переменная с текстом инструкции |
| `list[dict[str, object]]` | Подсказка: список словарей со строковыми ключами |

Для теста `pwd` начальная история содержала два сообщения:

```text
messages[0] --> system: правила работы агента
messages[1] --> user: вызови bash с pwd один раз и заверши
```

Список создан в памяти. Запрос к API на этом шаге ещё не отправлен.

## 7. Как начинается очередной ход

```python
for turn in range(1, MAX_TURNS + 1):
    print(f"\n{'='*60}\n🔄 Turn {turn}\n{'='*60}")
    content, tool_calls = call_llm(messages)
```

`range(1, MAX_TURNS + 1)` выдаёт целые числа от 1 до `MAX_TURNS` включительно. Правая граница у `range()` не включается, поэтому при `MAX_TURNS = 1000` используется `range(1, 1001)`.

`turn` получает очередное значение цикла. `{'='*60}` в f-строке повторяет символ `=` 60 раз. `\n` обозначает перевод строки. Этот вывод показывает человеку номер хода и не передаётся модели.

```python
content, tool_calls = call_llm(messages)
```

Функция возвращает пару значений, которую Python раскладывает в две переменные. Этот приём называется распаковкой:

```python
example_result = ("ответ", [])
content_example, tool_calls_example = example_result
```

## 8. Как `call_llm()` собирает запрос

В [строках 58–67](https://github.com/alanbigulov/chebupelka-jev/blob/f6108317f85553eb6acdec7dc94fe13ba115b367/chebupelkajev.py#L58):

```python
def call_llm(messages):
    payload = {
        "model": LLM_MODEL,
        "messages": messages,
        "tools": LLM_TOOLS,
        "tool_choice": "auto",
        "thinking": {"type": "disabled"},
        "temperature": 0.1,
        "max_tokens": 4096,
    }
```

`payload` является обычным словарём Python. Значения `messages` и `LLM_TOOLS` включают вложенные списки и словари. Библиотека `requests` затем преобразует их в JSON.

`tool_choice="auto"` позволяет модели самой решить, нужен ли инструмент. Это не команда «обязательно вызвать `bash`». В тесте мы дополнительно попросили об этом текстом пользовательской задачи.

`thinking={"type": "disabled"}` относится к конфигурации выбранного провайдера. В v0.1.0 режим рассуждений не поддерживается историей сообщений, поскольку `reasoning_content` не сохраняется. Его развитие намечено в `EDU-08` [roadmap](../development-roadmap.md).

## 9. Где действительно отправляется HTTP-запрос

```python
llm_http_response = requests.post(
    f"{LLM_BASE_URL}/chat/completions",
    json=payload,
    headers=LLM_HEADERS,
)
llm_http_response.raise_for_status()
```

| Выражение | Результат |
|---|---|
| `f"{LLM_BASE_URL}/chat/completions"` | Адрес `https://api.deepseek.com/chat/completions` |
| `json=payload` | JSON-тело запроса |
| `headers=LLM_HEADERS` | Тип содержимого и авторизация |
| `requests.post(...)` | Ожидание HTTP-ответа сервера |
| `raise_for_status()` | Исключение при HTTP-ошибке 4xx или 5xx |

Первая сессия получила `HTTP: 200` в отдельном тестовом запросе. В самом `call_llm()` статус не печатается, но проверяется.

В текущем `requests.post()` нет `timeout`. Таймаут 60 секунд был только в отдельном тестовом фрагменте; таймаут 120 секунд относится к команде `subprocess`, которую разберём ниже. Обработка HTTP-таймаутов и ошибок относится к `EDU-02`.

## 10. Как извлекается сообщение модели

```python
msg = llm_http_response.json()["choices"][0]["message"]
content = (msg.get("content") or "").strip()
tool_calls = msg.get("tool_calls") or []
return content, tool_calls
```

Ответ ожидается примерно такой формы:

```json
{
  "choices": [
    {
      "message": {
        "role": "assistant",
        "content": null,
        "tool_calls": [
          {
            "id": "example_call_id",
            "type": "function",
            "function": {
              "name": "bash",
              "arguments": "{\"command\": \"pwd\"}"
            }
          }
        ]
      }
    }
  ]
}
```

Это пример структуры, а не полный зафиксированный ответ API. `example_call_id` является учебным значением.

| Шаг | Что берём |
|---|---|
| `.json()` | Разбираем HTTP-тело как JSON |
| `["choices"]` | Список вариантов ответа |
| `[0]` | Первый вариант |
| `["message"]` | Сообщение модели |

`.get("content")` возвращает значение ключа или `None`, если ключ отсутствует. Выражение `or ""` подставляет пустую строку, если полученное значение ложно, например `None` или `""`. `.strip()` убирает пробельные символы с краёв.

То же правило `or` используется для списка инструментов. При отсутствии списка `tool_calls` становится `[]`.

Программа предполагает правильные типы и форму ответа. Например, отсутствие `choices` приведёт к `KeyError`, а пустой `choices` к `IndexError`. Эти случаи не перехватываются внутри `call_llm()`.

## 11. Как цикл решает, печатать ли текст и завершаться ли

После возврата из `call_llm()`:

```python
if content:
    print(f"\n🤖 {content}")

if not tool_calls:
    print("(no text output)" if not content else "")
    print("✅ Agent finished")
    return
```

Это два независимых `if`. Если есть и текст, и инструменты, программа сначала напечатает текст, затем выполнит инструменты.

| Текст | Инструменты | Действие |
|---|---|---|
| Есть | Нет | Напечатать текст и завершиться |
| Нет | Есть | Перейти к инструментам |
| Есть | Есть | Напечатать текст и перейти к инструментам |
| Нет | Нет | Напечатать `(no text output)` и завершиться |

`return` выходит из всей функции `agent_loop()`. Для выхода только из цикла использовался бы `break`, но в этой строке его нет.

В тесте ход 1 вернул инструмент, поэтому выполнение продолжилось. Ход 2 вернул ответ с директорией без инструментов, поэтому функция завершилась.

## 12. Как разбирается запрос инструмента

```python
prefix = "\n" if content else ""

for tool_call in tool_calls:
    function = tool_call["function"]["name"]
    arguments = json.loads(tool_call["function"]["arguments"])
    tool_call_id = tool_call["id"]
```

`prefix` нужен для оформления терминала. Если текст модели уже напечатан, перед инструментом добавляется перенос строки.

`for tool_call in tool_calls` последовательно перебирает все элементы ответа. Название переменной `function` содержит строку с именем инструмента, а не Python-функцию.

В нашем примере:

```python
function == "bash"
arguments == {"command": "pwd"}
tool_call_id == "example_call_id"
```

Последнее значение приведено как пример, реальный идентификатор не печатался.

Поле `arguments` внутри ответа содержит JSON-строку. `json.loads()` разбирает её:

```text
'{"command": "pwd"}'       строка
          |
          v
     json.loads()
          |
          v
{"command": "pwd"}         словарь
```

Некорректный JSON вызовет исключение на этом шаге, до входа в `call_tool()`. Здесь пока нет `try/except`; обработка исключений внутри следующей функции не перехватит ошибку, возникшую до её вызова. Это часть `EDU-03`.

## 13. Как показывается запрос и вызывается инструмент

```python
print(f"{prefix}🔧 Tool: {function}({json.dumps(arguments, ensure_ascii=False)})")
result = call_tool(function, arguments)
print(f"   → {result[:500]}{'...' if len(result)>500 else ''}")
```

`json.dumps()` преобразует Python-объект в JSON-строку для печати. `ensure_ascii=False` оставляет русские буквы читаемыми. Это обратное направление относительно `json.loads()`, но здесь оно требуется только для вывода.

```text
API arguments --> json.loads() --> словарь --> call_tool()
                                      |
                                      `--> json.dumps() --> печать для пользователя
```

`result[:500]` берёт первые 500 символов результата. Условное выражение добавляет `...`, если он длиннее. Полный `result` остаётся в переменной и позже отправляется модели.

## 14. Как `call_tool()` выбирает функцию

В [строках 48–55](https://github.com/alanbigulov/chebupelka-jev/blob/f6108317f85553eb6acdec7dc94fe13ba115b367/chebupelkajev.py#L48):

```python
def call_tool(name: str, arguments: dict) -> str:
    func = {"bash": run_bash}.get(name)
    if not func:
        return f"Error: unknown tool '{name}'"
    try:
        return func(**arguments)
    except Exception as e:
        return f"Error calling {name}: {e}"
```

Словарь создаёт связь между именем и функцией:

```text
"bash" --> run_bash
```

`run_bash` без скобок обозначает сам объект функции. Скобки появились бы при вызове `run_bash(...)`.

`.get(name)` ищет ключ. Для `"bash"` он возвращает функцию, для неизвестного имени `None`. Поэтому неизвестный инструмент превращается в строку ошибки без локального выполнения.

В текущем файле нет отдельной переменной `TOOLS_MAP`. Соответствие задано прямо словарём внутри `call_tool()`. Для расширения агента потребуется согласовать его с `LLM_TOOLS`.

## 15. Что делает `**arguments`

```python
func(**arguments)
```

`**` распаковывает словарь в именованные параметры:

```python
arguments = {"command": "pwd"}

# Для выбранного func обе записи означают одно и то же:
func(**arguments)
run_bash(command="pwd")
```

Ключ `command` становится именем параметра, а значение `"pwd"` его содержимым.

| Пример данных | Результат текущего вызова |
|---|---|
| `{"command": "pwd"}` | Вызов `run_bash(command="pwd")` |
| `{}` | Исключение о недостающем аргументе, затем строка ошибки |
| `{"other": "pwd"}` | Исключение о неизвестном параметре, затем строка ошибки |

`except Exception as e` перехватывает обычные исключения, возникшие внутри этого `try`, и преобразует их в текст. Тогда результат ошибки может быть передан модели как результат инструмента.

Аннотация `arguments: dict` сама не проверяет данные. `json.loads()` может вернуть и другой JSON-тип. Локальная валидация перед распаковкой пока отсутствует.

## 16. Где запускается команда на компьютере

В [строках 39–45](https://github.com/alanbigulov/chebupelka-jev/blob/f6108317f85553eb6acdec7dc94fe13ba115b367/chebupelkajev.py#L39):

```python
def run_bash(command: str) -> str:
    try:
        command_result = subprocess.run(
            command,
            shell=True,
            capture_output=True,
            text=True,
            timeout=120,
        )
        out = command_result.stdout + (
            f"\nSTDERR:\n{command_result.stderr}"
            if command_result.stderr else ""
        )
        return f"Exit code: {command_result.returncode}\n{out}"
    except subprocess.TimeoutExpired:
        return "Error: command timed out after 120s"
```

| Параметр | Что делает |
|---|---|
| `command` | Передаёт строку команды |
| `shell=True` | Запускает её через системную оболочку |
| `capture_output=True` | Собирает `stdout` и `stderr` вместо прямой печати |
| `text=True` | Возвращает вывод строками Python |
| `timeout=120` | Ограничивает ожидание выполнения 120 секундами |

При таком вызове на macOS обычно используется `/bin/sh`. Имя `run_bash` не выбирает `/bin/bash`. Оболочка получает командную строку, поэтому она понимает перенаправления, конвейеры и другие элементы shell-синтаксиса, поддерживаемые выбранной оболочкой.

Параметр `cwd` отсутствует. Команда выполняется в унаследованной текущей директории. При запуске из папки репозитория `pwd` возвращает путь этой папки.

Параметр `env` также отсутствует. Команды наследуют окружение агента, включая ключ API. Подтверждение и изоляция описаны как будущая работа в `EDU-04` и `EDU-05`.

## 17. Как читаются `stdout`, `stderr` и код завершения

Объект `command_result` содержит:

| Поле | Смысл | Значение для успешного `pwd` |
|---|---|---|
| `stdout` | Обычный вывод | Путь и перевод строки |
| `stderr` | Диагностический вывод | Пустая строка |
| `returncode` | Код завершения команды | `0` |

Строка сборки `out` добавляет `stderr` только при его наличии:

```python
out = command_result.stdout + (
    f"\nSTDERR:\n{command_result.stderr}"
    if command_result.stderr else ""
)
```

Затем функция возвращает строку:

```text
Exit code: 0
/Users/alanbigulov/Projects/chebupelka-jev
```

Ненулевой `returncode` не вызывает исключение автоматически, потому что нет `check=True`. Если команда завершилась с ошибкой, код и вывод всё равно возвращаются модели. `stderr` тоже не всегда означает ошибку: некоторые программы пишут туда обычную диагностику.

При превышении таймаута `subprocess.run()` выбрасывает `TimeoutExpired`, а функция возвращает указанный текст. Завершение всех потомков shell-процесса в v0.1.0 отдельно не настроено; это тема `EDU-10`.

## 18. Как результат попадает в память беседы

Возвращаемся в `agent_loop()` к [строкам 97–98](https://github.com/alanbigulov/chebupelka-jev/blob/f6108317f85553eb6acdec7dc94fe13ba115b367/chebupelkajev.py#L97):

```python
messages.append({
    "role": "assistant",
    "content": content or None,
    "tool_calls": [tool_call],
})
messages.append({
    "role": "tool",
    "tool_call_id": tool_call_id,
    "content": result,
})
```

`append()` добавляет один элемент в конец существующего списка. Сначала сохраняется сообщение модели с запросом инструмента, затем результат локального выполнения.

`content or None` записывает `None`, если текст пустой. При JSON-сериализации Python `None` станет `null`. Сам `tool_call` сохраняет идентификатор, имя функции и строку аргументов из ответа модели.

| Сообщение | Для чего нужно |
|---|---|
| `assistant` с `tool_calls` | Модель видит, какое действие ранее запросила |
| `tool` с `tool_call_id` | Модель видит результат именно этого действия |

После `pwd` список вырос с двух сообщений до четырёх:

```text
0  system     инструкция
1  user       задача
2  assistant  запрос bash с pwd
3  tool       код завершения и путь
```

Результат пока находится только в Python-списке. На сервер он уйдёт при следующем вызове `call_llm(messages)`.

## 19. Почему в терминале появились два хода

После обработки инструментов внешний `for` берёт следующее значение `turn`. На втором ходе повторно выполняется строка 82:

```python
content, tool_calls = call_llm(messages)
```

Но теперь `messages` содержит вывод команды. Модель отвечает уже с учётом полученного пути.

```text
Ход 1
  [system, user] --> DeepSeek
                         |
                         v
                    bash("pwd")
                         |
                         v
                 локальное выполнение
                         |
                         v
            append assistant, append tool
                         |
                         v
Ход 2
  [system, user, assistant, tool] --> DeepSeek
                                         |
                                         v
                                текст без tool_calls
                                         |
                                         v
                                 печать и return
```

Один вызов инструмента потребовал двух обращений к модели: выбрать действие и интерпретировать результат. Для более длинной задачи цикл может повторяться много раз.

## 20. Что происходит при достижении предела

После цикла есть [строка 99](https://github.com/alanbigulov/chebupelka-jev/blob/f6108317f85553eb6acdec7dc94fe13ba115b367/chebupelkajev.py#L99):

```python
print(f"\n⚠️  Max turns ({MAX_TURNS}) reached. Stopping.")
```

Если модель продолжает возвращать инструменты на каждом ходе, после 1000 ходов цикл заканчивается, печатается сообщение и функция естественно возвращает `None`.

В этой ветке нет `sys.exit(1)`. При отсутствии другого исключения процесс Python может завершиться с обычным кодом 0, хотя текст сообщает о достигнутом пределе. Отдельный контракт кодов завершения и лимитов можно изучить при развитии `EDU-09`.

В нашем тесте до строки 99 выполнение не дошло, потому что на втором ходе сработал `return` на строке 88.

## 21. Что сохраняем как известное ограничение v0.1.0

Строки добавления сообщений находятся внутри `for tool_call in tool_calls`. Для одного инструмента это соответствует проверенному примеру. Для нескольких инструментов модельное сообщение дробится:

```text
Ответ API:               История текущего кода:
assistant [A, B]         assistant [A]
                         tool result A
                         assistant [B]
                         tool result B
```

Кроме изменения структуры, текст `content` при наличии может быть записан повторно для каждого вызова. Будущее исправление должно сохранить исходное `assistant` со всем списком вызовов и затем добавить результаты каждого инструмента. Это `EDU-01`; в данном выпуске мы его не вносили.

| Ограничение | Откуда видно в коде | Пункт roadmap |
|---|---|---|
| HTTP без явного таймаута | Вызов `requests.post()` на строке 68 | `EDU-02` |
| Ответ и аргументы не проверяются до выполнения | Прямые обращения к полям и `json.loads()` | `EDU-03` |
| Команда запускается без подтверждения | Прямой переход `call_tool()` к `run_bash()` | `EDU-04` |
| Унаследованное окружение и доступ к файловой системе | Нет `cwd`, `env` и изоляции | `EDU-05` |
| История нескольких вызовов изменяет исходное сообщение | `append()` внутри цикла инструментов | `EDU-01` |
| Ограничена только печать вывода | `result[:500]`, но в истории полный `result` | `EDU-09` |
| Режим рассуждений выключен | `thinking` без хранения `reasoning_content` | `EDU-08` |

Рабочие статусы, целевые версии и критерии проверки находятся в [development-roadmap.md](../development-roadmap.md). Таблица урока объясняет конкретную исходную версию и не заменяет трекинг.

## 22. Небольшие упражнения без обращения к API

Эти упражнения разбирают Python-выражения отдельно. Они не импортируют агент, не требуют ключа и не выполняют запросов к DeepSeek.

В терминале из папки проекта можно выполнить:

```bash
"$(brew --prefix)/bin/uv" run python - <<'PY'
import json

argv_example = ["chebupelkajev.py", "Выполни", "pwd"]
print("Имя файла:", argv_example[0])

arguments_example = json.loads('{"command": "pwd"}')
print("Тип аргументов:", type(arguments_example).__name__)

messages_example = [{"role": "user", "content": "пример"}]
messages_example.append({"role": "tool", "content": "результат"})
print("Число сообщений:", len(messages_example))
PY
```

Затем объясни своими словами:

1. Почему имя файла пропущено при сборке задачи?
2. Почему для аргументов инструмента требуется `json.loads()`, хотя HTTP-ответ уже разбирался через `.json()`?
3. Чем пустой список инструментов отличается от списка с одним инструментом при проверке `if not tool_calls`?
4. Что передаётся в API после `append()`, а что только печатается в терминал?
5. Почему `returncode=1` и исключение `TimeoutExpired` идут по разным веткам?
