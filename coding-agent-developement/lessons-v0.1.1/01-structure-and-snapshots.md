# Урок 1. Структура проекта и учебные снимки v0.1.1

В v0.1.1 код агента, зависимости и локальные проверки собраны в `agent/`.
Уроки v0.1.0 читаются по сохранённому коммиту, а старая версия запускается в отдельной рабочей копии.
Так можно развивать текущий проект и повторять прошлое занятие с его исходниками.

```text
Одна история Git
       |
       +--> текущая копия v0.1.1 --> agent/ --> agent/.venv/
       |
       `--> отдельная копия v0.1.0 --> корень --> .venv/

Урок версии --> паспорт --> тег --> полный SHA --> файлы коммита
```

## 1. Зачем выделять `agent/`

У исполняемой программы и учебного материала разные задачи.
Программа принимает запрос пользователя и обращается к DeepSeek.
Учебные документы объясняют устройство проекта и сохраняют прошлые занятия.
Папка `agent/` собирает файлы, которые нужны именно для запуска и проверки программы.

| Часть | Что хранит |
|---|---|
| `agent/` | Python-файл, настройки зависимостей, тесты и своё окружение |
| `coding-agent-developement/` | Карту проекта, план развития и уроки по версиям |
| Корень репозитория | Общий README, историю изменений и правила версий |

Это организационная граница внутри одного репозитория.
Четыре функции пока находятся в одном `chebupelkajev.py`.
Перенос в папку не создаёт сервер и не добавляет фреймворк агентов.
Байты Python-файла совпадают с v0.1.0.

Поведение программы разобрано в [старом уроке об архитектуре](../lessons-v0.1.0/02-agent-architecture.md).
Здесь изучаем расположение файлов, выбор окружения и сохранение снимка.

## 2. Как изменилась структура

В снимке v0.1.0 Python-проект лежал прямо в корне:

```text
chebupelka-jev/
|-- chebupelkajev.py
|-- pyproject.toml
|-- uv.lock
|-- .python-version
|-- .venv/                         локальная папка, не в Git
|-- README.md
|-- VERSIONING.md
|-- CHANGELOG.md
`-- coding-agent-developement/
    `-- lessons-v0.1.0/
```

Рабочая структура v0.1.1:

```text
chebupelka-jev/
|-- agent/
|   |-- chebupelkajev.py
|   |-- pyproject.toml
|   |-- uv.lock
|   |-- .python-version
|   |-- .venv/                     текущее локальное окружение
|   `-- tests/
|       |-- test_agent.py
|       `-- fixtures/
|           |-- text_response.json
|           `-- pwd_tool_cycle.json
|-- .venv/                         прежнее локальное окружение сохранено
|-- README.md
|-- VERSIONING.md
|-- CHANGELOG.md
`-- coding-agent-developement/
    |-- project-structure.md
    |-- development-roadmap.md
    |-- lessons-v0.1.0/
    `-- lessons-v0.1.1/
```

Здесь показаны файлы, необходимые для сравнения двух версий.
Полная карта находится в [project-structure.md](../project-structure.md).
Папки `.venv/` локальные; после клонирования их создаёт `uv`.

## 3. Почему рабочая директория меняет запуск

`uv` определяет Python-проект по его настройкам.
В v0.1.0 `pyproject.toml` находится в корне старой копии.
В v0.1.1 он находится внутри `agent/`.
Команды следует выполнять из директории соответствующего проекта.

| Версия | Директория перед командой | Имя файла для запуска |
|---|---|---|
| v0.1.0 | Корень worktree `chebupelkajev-v0.1.0/` | `chebupelkajev.py` |
| v0.1.1 | `chebupelka-jev/agent/` | `chebupelkajev.py` |

Из корня текущего репозитория:

```bash
cd agent
uv sync --locked
uv run --locked python --version
uv run --locked python -c 'import sys; print(sys.executable)'
```

`sys.executable` показывает интерпретатор, который выполнил программу.
В текущем проекте ожидается путь внутри `agent/.venv/`.
Название активного Conda-окружения в приглашении терминала само по себе этого не доказывает.

В обычном запуске команда агента выглядит так:

```bash
uv run --locked python chebupelkajev.py "текст задачи"
```

Эта команда обращается к провайдеру и требует ключ в окружении процесса.
Для проверок структуры и двух локальных сценариев ниже она не нужна.

`run_bash()` наследует рабочую директорию процесса агента.
Поэтому `pwd` в v0.1.1, запущенной из `agent/`, покажет эту папку.
Выбор директории определяет относительные пути, но не ограничивает доступ инструмента к другим файлам.

## 4. Зачем два окружения

Окружение содержит интерпретатор и установленные пакеты.
Оно не входит в коммит и не является учебным снимком.
Снимок хранит требования, lock-файл и исходники, по которым окружение создают снова.

| Папка | Назначение |
|---|---|
| `chebupelka-jev/agent/.venv/` | Работа с текущим Python-проектом |
| `chebupelka-jev/.venv/` | Прежнее локальное окружение, оставлено для отката |
| `chebupelkajev-v0.1.0/.venv/` | Отдельное окружение старого снимка |

Старую корневую `.venv/` не удаляем во время переноса.
Она не заменяет окружение нового `agent/`.
Рабочая копия v0.1.0 тоже получает собственную `.venv/`.
Копировать готовое окружение между папками не нужно; внутри могут быть абсолютные пути.

`uv sync --locked` устанавливает версии из `uv.lock` и проверяет согласованность требований.
Если требования изменились без обновления lock-файла, команда сообщает об этом.
Для повторения занятия такое поведение помогает заметить смешение конфигураций.

## 5. Чем тег отличается от полного SHA

Коммит сохраняет дерево файлов и информацию о его месте в истории.
Полный SHA идентифицирует этот коммит.
Тег даёт коммиту короткое имя выпуска, например `v0.1.0`.

```text
v0.1.0
   |
   v
f6108317f85553eb6acdec7dc94fe13ba115b367
   |
   +--> chebupelkajev.py
   +--> pyproject.toml
   `--> uv.lock
```

Выпущенный тег по правилам проекта не переносят на новый коммит.
Технически Git позволяет заменить тег, поэтому полный SHA полезен для строгой проверки.
Старые уроки ссылаются на GitHub-файлы по полному SHA v0.1.0.
Эти ссылки сохраняют старые пути даже после переноса текущего файла в `agent/`.

Из корня репозитория:

```bash
git rev-parse 'v0.1.0^{}'
git show v0.1.0:chebupelkajev.py
git show v0.1.0:pyproject.toml
```

Первая команда должна вернуть SHA со схемы выше.
Две следующие читают файлы из коммита и не меняют рабочую копию.
Для v0.1.1 после создания тега используй `git rev-parse 'v0.1.1^{}'`.
Собственный SHA выпуска не вписывают в файл того же коммита; правило объяснено в [паспорте](version.md).

## 6. Как открыть старую версию рядом с текущей

Worktree создаёт дополнительную рабочую копию одной истории Git.
У неё отдельные рабочие файлы и индекс.
История коммитов и настройки удалённых адресов остаются общими.

Если соседняя копия ещё не создана, выполни из корня `chebupelka-jev/`:

```bash
git worktree add --detach ../chebupelkajev-v0.1.0 v0.1.0
cd ../chebupelkajev-v0.1.0
git rev-parse HEAD
uv sync --locked
uv run --locked python --version
uv run --locked python -c 'import requests; print(requests.__version__)'
```

Путь начинается с `../`, поэтому старая копия будет соседней папкой.
`HEAD` должен совпасть с `f6108317f85553eb6acdec7dc94fe13ba115b367`.
`uv sync` выполняется в корне старой копии, где лежит её `pyproject.toml`.
Эта команда создаёт отдельное окружение старой версии.

Если worktree уже создан, повторять `add` не нужно.
Посмотреть существующие копии можно командой `git worktree list`.
Затем перейди в нужную папку и проверь `HEAD`.

`--detach` означает, что `HEAD` указывает прямо на коммит, а не на ветку.
Текущая ветка основной рабочей копии при этом не переключается.
Для чтения, установки зависимостей и повторения запуска этого достаточно.

Для собственных изменений старого кода создай учебную ветку внутри старой копии:

```bash
git switch -c lab/v0.1.0
```

Теперь новые коммиты будут принадлежать этой ветке.
Команды старых уроков запускай в старой копии, команды нового урока в `agent/` текущей.
Историческое объединение с авторским репозиторием заново выполнять не требуется.

## 7. Что проверяется без DeepSeek

Два теста проверяют существующий цикл на заранее подготовленных ответах.
`requests.post` заменяется локальной функцией, которая возвращает данные fixtures.
Реальный API не вызывается, ключ провайдера для этих тестов не нужен.

| Сценарий | Данные | Наблюдаемый результат |
|---|---|---|
| Обычный ответ | `text_response.json` | Текст выводится, цикл завершается без команды |
| Один `bash` с `pwd`, затем ответ | `pwd_tool_cycle.json` | Во втором запросе есть результат и правильный `tool_call_id`, затем цикл завершается |

Fixtures синтетические: они описывают нужную форму ответа, а не запись облачной сессии.
Сценарий `pwd` допускает один безопасный локальный запуск через перехватчик команд.
Он проверяет передачу настоящего вывода команды обратно в историю.

Из `agent/`:

```bash
uv run --locked python -m unittest discover -s tests -v
```

Успешный результат относится только к двум описанным сценариям.
Он не подтверждает обработку нескольких инструментов, HTTP-ошибок или некорректного JSON.
Эти задачи остаются в [плане развития](../development-roadmap.md).

## 8. Что воспроизводится, а что зависит от провайдера

| Составляющая | Что фиксирует снимок | Что проверять отдельно |
|---|---|---|
| Python-код | Байты файла в коммите | Запуск нужного файла из нужной копии |
| Зависимости | Версии и хеши в `uv.lock` | Доступность пакетов или локального кеша |
| Python | Минимум `>=3.10`, выбор ветки `3.14` | Фактический патч через `python --version` |
| Локальная проверка | Fixtures и утверждения тестов | Результат запуска тестов |
| Модель | Строку `deepseek-flash` в настройках | Реализацию и доступность у провайдера |
| Сеть | URL API в исходнике | Соединение, авторизацию и состояние сервиса |

Первая учебная сессия использовала Python `3.14.7` и Requests `2.34.2`.
Файл `.python-version` содержит `3.14`, поэтому новый запуск может выбрать другой патч этой ветки.
Lock-файл сохраняет версии Python-пакетов, но не состояние DeepSeek.
Даже один исходник и одна строка модели не гарантируют одинаковый облачный ответ.

`DEEPSEEK_API_KEY` передаётся только через окружение процесса.
Его значение не сохраняют в Git, уроке, паспорте или fixtures.
В подготовке v0.1.1 облачные проверки первой сессии не повторяются.
