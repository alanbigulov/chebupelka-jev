# Структура проекта chebu и история её развития

Базовое разделение введено в **v0.1.1**. Исполняемый агент находится в `agent/`, учебный модуль в `coding-agent-developement/`. В корне остаются документы, относящиеся ко всему репозиторию. Схема ниже фиксирует v0.1.4 и включает дополнения, отсутствующие в теге v0.1.1. С v0.1.3 проект и исходник агента называются `chebu`; в снимках v0.1.0–v0.1.2 сохранено прежнее имя `chebupelkajev`.

Этот документ объясняет решения о размещении файлов и сохраняет журнал изменений структуры. Практические команды разобраны в [уроке v0.1.1](lessons-v0.1.1/01-structure-and-snapshots.md). Учебный смысл задач находится в [roadmap](development-roadmap.md), актуальное состояние в [GitHub Project](https://github.com/users/alanbigulov/projects/4) и связанных issues. Выпуски описаны в [CHANGELOG.md](../CHANGELOG.md).

## 1. Почему разделили проект сейчас

В v0.1.0 один Python-файл и его настройки лежали рядом с общей документацией. Для первого запуска этого было достаточно. После появления подробных уроков у репозитория возникли две самостоятельные области развития:

| Область | Что меняется | Кому нужны файлы |
|---|---|---|
| Исполняемый агент | Код, зависимости, тесты, способы запуска | Разработчику и пользователю агента |
| Учебный модуль | Объяснения, упражнения, паспорта версий, учебный план | Читателю курса и участнику занятий |
| Общие документы | Обзор, правила версий, история выпусков | Всем участникам проекта |

Разделение помогает находить нужные файлы и независимо расширять обе области. Оно не требует отдельного Git-репозитория для каждой области: один тег может закрепить одновременно код и соответствующие материалы.

## 4. Правила размещения новых файлов

| Новый файл | Место | Причина |
|---|---|---|
| Реализация агента или его инструментов | `agent/` | Относится к исполняемому проекту |
| Проверка поведения | `agent/tests/` | Может выполняться без чтения курса |
| Синтетический ответ API для теста | `agent/tests/fixtures/` | Данные проверки отделены от объяснений |
| Зависимости Python | `agent/pyproject.toml`, `agent/uv.lock` | Учебные Markdown-файлы не являются Python-проектом |
| Урок конкретного выпуска | `coding-agent-developement/lessons-vX.Y.Z/` | Сохраняется соответствие изучаемому коду |
| Паспорт выпуска для уроков | `lessons-vX.Y.Z/version.md` | Указывает тег, пути, окружение и проверки |
| Текст и критерии учебной задачи | `coding-agent-developement/tickets/EDU-NN.md` | Ученик читает задачу после клонирования, текст замораживается вместе с тегом |
| Учебный смысл намечаемой доработки | `development-roadmap.md` | Пояснение и ссылка на тикет; критерии находятся в файле тикета, этап в трекере |
| Решение о каталогах и границах модулей | `project-structure.md` | Сохраняются причина и последствия |
| Правила учёта задач | `project-tracking.md` | Трекером служит снимок сессии; GitHub подключается как адаптер |
| Правила для ведущего агента | Корневой `AGENTS.md`; `CLAUDE.md` только указывает на него | Каждый рантайм читает один файл, правила не расходятся |
| Протокол, шаблон и скрипт передачи сессии | `.handoff/README.md`, `TEMPLATE.md`, `handoff.py`, в Git | Новый clone и git worktree получают один протокол |
| Состояние сессии: снимок и архив | `.handoff/SESSION.md` и `.handoff/archive/`, исключены из Git | Агенты передают контекст без публикации локальных записей |
| Факты о рантайме | `runtime-config/runtimes/<id>.json` и строка в `manifest.json` | Скрипт распознаёт рантайм и печатает команды запуска по данным, без правки кода |
| Правила учебного сопровождения | `coding-agent-developement/tutor-modes.md` | Режим выбирает ученик, и правила режима одинаковы в каждом рантайме |
| Примеры режима `sandbox` | Корневая `.sandbox/`, исключённая из Git | Агент показывает поведение на копии и не меняет код проекта |
| Реализованное изменение версии | Корневой `CHANGELOG.md` | Общий журнал фактов |
| Документация, код и скрипты навыка `chebu-tutor` | `chebu-tutor-skill/`, документация в `chebu-tutor-skill/chebu-tutor-docs/` | У навыка своя версия и свои проверки, отдельные от `agent/` и учебного модуля |

Корневой README объясняет устройство всего проекта и направляет читателя в нужный модуль. `agent/README.md` отвечает за актуальные команды запуска. Учебный README задаёт порядок занятий.

## 5. Окружения и текущая директория

После переноса Python-проект начинается в `agent/`. Начни из корня репозитория; первая команда ниже переходит в `agent/`. Команды подготовки и тестов выполняются после этого перехода:

```bash
cd agent
uv sync --locked
uv run python -m unittest discover -s tests -v
```

Проект проверен с uv 0.5.15 и 0.12.14.

```text
Текущий репозиторий
├── .venv/             прежнее окружение, сохранено для отката
└── agent/.venv/       актуальное окружение Python-проекта

Соседний worktree v0.1.0, если развёрнут
└── .venv/             отдельное окружение старого выпуска
```

Соседний worktree v0.1.0 удалён с учебной машины после выпуска v0.1.3 и создаётся заново по [VERSIONING.md](../VERSIONING.md). Эти окружения не хранятся в Git. Шаблон `.venv` в корневом `.gitignore` исключает одноимённые каталоги на любой глубине. Старое корневое окружение сохранено локально; его наличие не является частью выпуска. Новые установки используют только `agent/.venv`.

У shell-инструмента не указан `cwd`, поэтому рабочая директория запуска влияет на результат `pwd` и относительные пути команд. В новом обычном запуске из `agent/` рабочей директорией будет `agent/`. Это изменение способа запуска, а не изменение функции `run_bash()`.

## 6. Снимок версии и рабочая папка

```text
Общая история Git
   ├── тег v0.1.0 --> исходники в корне
   ├── тег v0.1.1 --> исходники в agent/
   ├── тег v0.1.2 --> agent/ и урок о GitHub-трекинге
   ├── тег v0.1.3 --> agent/chebu.py после переименования
   └── тег v0.1.4 --> AGENTS.md, .handoff/ и tickets/
          |
          +--> main: дальнейшая работа

Отдельные рабочие деревья
   ├── chebupelka-jev/          текущий main
   └── chebupelkajev-v0.1.0/    detached снимок старой версии, создаётся при необходимости
```

Тег является ссылкой на коммит, а не папкой с копией исходников. `git worktree` разворачивает выбранный коммит в отдельный каталог, используя общую историю. Рабочие файлы и `.venv` при этом отдельные; worktree не является изолированной системой безопасности.

Не сохраняем повторные копии всей кодовой базы в папках уроков. Они быстро расходятся с реальной версией и затрудняют проверку происхождения. Для точного снимка достаточно тега и SHA; для удобного запуска создаём worktree.

## 7. Как уроки переживают изменения кода

Старые уроки сохраняют исторические команды и версии. Ссылки на изучаемые исходники и настройки закрепляются за старым тегом или SHA. Относительные ссылки на другие уроки и общие документы остаются внутри репозитория.

| Материал | Источник кода | Каталог команд в снимке |
|---|---|---|
| [v0.1.0](lessons-v0.1.0/version.md) | `v0.1.0:chebupelkajev.py` | Корень worktree |
| [v0.1.1](lessons-v0.1.1/version.md) | `v0.1.1:agent/chebupelkajev.py` | `agent/` внутри worktree |
| [v0.1.2](lessons-v0.1.2/version.md) | `v0.1.2:agent/chebupelkajev.py` | `agent/` внутри worktree |
| [v0.1.3](lessons-v0.1.3/version.md) | `v0.1.3:agent/chebu.py` | `agent/` внутри worktree |
| [v0.1.4](lessons-v0.1.4/version.md) | `v0.1.4:agent/chebu.py` | `agent/` внутри worktree |

Паспорт новой версии ссылается на тег и даёт команду получения полного SHA. Записать собственный окончательный SHA внутри того же коммита невозможно: изменение документа создаст другой SHA. Паспорт v0.1.0 может содержать полный SHA, поскольку этот коммит уже существует.

Git фиксирует исходники; lock-файл фиксирует пакеты. Ни один из них не фиксирует облачный сервис DeepSeek или ответы модели. Поэтому сохраняем настройки и результаты наблюдений, а работу самого Python-цикла дополнительно проверяем синтетическими ответами без сети.

## 8. Почему пока не разделяем Python-файл

Реализация содержит четыре небольшие функции и остаётся одним файлом. Каталог `agent/` отделяет проект от курса без новых внутренних слоёв. Разделение на пакеты, отдельные инструменты, конфигурацию и хранение состояния станет самостоятельной задачей, когда появится конкретная потребность.

Перед таким изменением нужно определить владельца каждого состояния, входные и выходные данные модулей и проверку сохранения поведения. Новая папка сама по себе не улучшает архитектуру.
