# Версии навыка chebu-tutor

У навыка своя версия, независимая от версии `chebu` (решение D-03 в [журнале](architecture.md#журнал-решений)). Версию `chebu` по-прежнему описывает [VERSIONING.md](../../VERSIONING.md). Этот документ описывает только навык.

## Источник номера

Номер хранится в поле `version` файла `chebu-tutor-skill/skill.json`. Остальные места получают номер из него:

```text
chebu-tutor-skill/skill.json: 0.1.0
        |
        +--> два адаптера: metadata.version 0.1.0
        +--> chebu-tutor-skill/CHANGELOG.md: [0.1.0]
        +--> Git-тег: chebu-tutor-v0.1.0
        `--> CHANGELOG.md проекта: одна строка о выпуске навыка
```

Адаптеры пишет генератор `tools/sync.py`, поэтому метка версии в них появляется сама. Проверка `sync.py --check` падает, если метка хотя бы одного адаптера отличается от `skill.json`. Шесть рантаймов читают два адаптера с одним текстом, поэтому разойтись по версии незаметно они не могут.

Метка лежит в поле `metadata.version` заголовка `SKILL.md`. Поле `metadata` входит в стандарт Agent Skills. Принимают ли его Claude Code и Codex без ошибки, проверяет этап 1 (вопрос 5 в [runtime-adapters.md](runtime-adapters.md)).

## Смысл номера

Схема `MAJOR.MINOR.PATCH`, как у `chebu`. До `1.0.0` навык экспериментальный.

| Часть | Когда повышать | Пример |
|---|---|---|
| PATCH | Исправление текста навыка или генератора без изменения поведения по контракту | Опечатка в строке использования, исправленный путь в адаптере |
| MINOR | Новое поведение, новый рантайм, новый режим или изменение контракта до 1.0 | Седьмой рантайм в `runtime-config/`, новый флаг после нового режима в TEMPLATE.md |
| MAJOR | Несовместимое изменение контракта после 1.0 | Другой синтаксис вызова или флагов |

Изменения вокруг навыка:

| Что изменилось | Версия навыка |
|---|---|
| Текст AGENTS.md или tutor-modes.md без смены режимов | Не меняется: навык ссылается на эти файлы и сразу работает по новому тексту |
| Перечисление режимов в TEMPLATE.md | `sync.py --check` падает. Нужен новый флаг, MINOR до 1.0 |
| Новый рантайм в `runtime-config/manifest.json` | `sync.py --check` падает до появления адаптера. Новый адаптер, MINOR |
| Схема снимка в TEMPLATE.md | Проверка `requires.handoff_schema` падает. Навык сверяется с новой схемой, MINOR до 1.0 |
| Выпуск новой версии `chebu` | Не меняется, если не нарушено `requires.chebu_min_version` |

## Совместимость с chebu

Поле `requires` в `skill.json` называет, на что навык опирается: схему снимка `handoff_schema` и минимальную версию `chebu_min_version`. Первая версия `chebu`, в которой есть AGENTS.md, режимы тьютора и `.handoff/`, это v0.1.4, поэтому навык не работает в снимках до v0.1.4. Список снимков и команды восстановления описывает VERSIONING.md.

## История изменений

Навык ведёт свой `chebu-tutor-skill/CHANGELOG.md` в формате корневого CHANGELOG: раздел `[Unreleased]` сверху и разделы выпусков `[X.Y.Z], ГГГГ-ММ-ДД` ниже. Файл создаёт этап 2.

[CHANGELOG.md](../../CHANGELOG.md) проекта остаётся общим журналом фактов. При выпуске навыка в его раздел `[Unreleased]` добавляется одна строка со ссылкой на раздел выпуска в CHANGELOG навыка.

## Теги

Тег навыка: аннотированный `chebu-tutor-vX.Y.Z`. Теги `chebu` остаются `vX.Y.Z`. Разные префиксы не дают двум линиям версий пересечься в `git tag --list`.

```bash
git tag --list 'chebu-tutor-v*'
git tag --list 'v*'
```

Тег создаётся только с разрешения владельца в текущей сессии, как требует AGENTS.md.

## Чек-лист выпуска навыка

Этап 7 выполняет этот список для первого выпуска. Следующие выпуски повторяют его.

1. Проверить, что рабочее дерево чистое и HEAD совпадает с `origin/main`.
2. Обновить `version` в `chebu-tutor-skill/skill.json`.
3. Выполнить `python3 chebu-tutor-skill/tools/sync.py`, затем `python3 chebu-tutor-skill/tools/sync.py --check`. Ожидаемый код выхода 0.
4. Выполнить тесты навыка и тесты `.handoff`. Все должны пройти.
5. Перенести записи из `[Unreleased]` в раздел новой версии CHANGELOG навыка. Добавить строку о выпуске в CHANGELOG проекта.
6. Записать в CHANGELOG навыка, в каких рантаймах выпуск прошёл приёмку и с каким результатом. Строки берутся из [verification.md](verification.md).
7. Получить разрешение владельца на коммит, push, PR и тег.
8. Создать коммит выпуска в ветке, отправить ветку и открыть PR. Владелец сливает PR через squash, и коммит выпуска получает в `main` новый SHA. Поэтому до слияния тег не ставится (D-28).
9. После слияния поставить аннотированный тег на коммит слияния и отправить тег. Коммит слияния называет `gh pr view <номер PR> -R alanbigulov/chebupelka-jev --json mergeCommit`:

```bash
git fetch origin
git tag -a chebu-tutor-vX.Y.Z <коммит слияния> -m "chebu-tutor X.Y.Z"
git push origin chebu-tutor-vX.Y.Z
```

10. Сверить локальный и удалённый коммит под тегом с коммитом слияния:

```bash
git rev-parse chebu-tutor-vX.Y.Z^{commit}
git ls-remote origin refs/tags/chebu-tutor-vX.Y.Z 'refs/tags/chebu-tutor-vX.Y.Z^{}'
```

Строка с `^{}` в выводе `ls-remote` называет коммит под тегом на origin.
