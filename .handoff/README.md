# Передача сессии между кодинговыми агентами

Эта папка переносит контекст учебной сессии из одного рантайма в другой: Codex, Claude Code, OpenCode, Grok, Cursor, Devin. Каждый агент читает этот протокол и заполняет один шаблон, поэтому сессию можно закрыть в одном рантайме и продолжить в другом.

Учеником здесь называется человек, который ведёт сессию и принимает решения. Слово «агент» без имени означает кодингового агента, который ведёт сессию. Агент, которого изучает проект, называется `chebu`. Прежнее имя `chebupelkajev` остаётся в архивных снимках, а в проекте только в именах файлов и ссылках на теги v0.1.0–v0.1.2. Репозиторий и каталог клона называются `chebupelka-jev`.

Снимок помогает продолжить работу. Фактическое состояние репозитория агент каждый раз проверяет заново.

Обновляй снимок после значимого этапа, перед паузой, перед сменой рантайма и перед потерей контекста. Уточняющий вопрос без новых действий снимка не требует.

## 1. Файлы и границы

```text
.handoff/
|-- README.md          этот протокол                    в Git
|-- TEMPLATE.md        схема снимка                     в Git
|-- handoff.py         старт, проверка и сохранение     в Git
|-- test_handoff.py    проверки скрипта                 в Git
|-- SESSION.md         последний законченный снимок     локально
|-- SESSION.next.md    снимок в подготовке              локально
`-- archive/           прежние снимки                   локально
```

Три последние строки называются состоянием. Состояние исключено из Git правилом `/.handoff/*` и остаётся на машине ученика.

| Файл | Когда читать | Когда менять |
|---|---|---|
| [README.md](README.md) | При старте и закрытии сессии | При согласованном изменении протокола, через Git |
| [TEMPLATE.md](TEMPLATE.md) | Перед созданием снимка | При изменении общей схемы, через Git |
| `SESSION.md` | В начале сессии | Только командой `handoff.py save` |
| `archive/` | Если `SESSION.md` отсутствует или нужна ссылка на прежнее решение | Только командой `handoff.py save` |

Границы состояния:

- Состояние не добавляется в индекс Git, в том числе через `git add -f`, и не отправляется во внешние сервисы.
- Новый clone получает протокол, шаблон и скрипт, но не получает состояние. Чтобы продолжить на другой машине, перенеси `SESSION.md` и `archive/` приватно.
- Состояние лежит в основном клоне. Когда агент работает в git worktree, `handoff.py` читает и пишет состояние основного клона. Снимок в подготовке агент пишет в `.handoff/` своей рабочей копии, и команда `save` переносит его в основной клон.
- Облачные сессии локальную папку не видят, поэтому в передаче не участвуют. Облачный агент работает по тикету и публичным документам, а его результат вносит в снимок следующая локальная сессия.

Снимок не заменяет задачу ученика, Git, тикеты и публичные документы проекта. Чтение и обновление состояния входит в передачу сессии. Коммит, push, изменение GitHub, выпуск и платный запуск API требуют разрешения ученика в текущей сессии.

## 2. Рантаймы

Список рантаймов хранит [manifest.json](../runtime-config/manifest.json). Факты о каждом рантайме лежат в `runtime-config/runtimes/<id>.json`: имя, CLI, входной файл, команды запуска, признак окружения. Поле `checked` отделяет подтверждённые факты от неподтверждённых.

Агент знает свой рантайм и называет его сам:

```bash
python3 .handoff/handoff.py start --runtime codex
```

Команда печатает конфигурацию названного рантайма и положение снимка. Для рантайма вне списка используй `--runtime unknown`. Протокол при этом выполняется так же.

Без ключа `--runtime` команда ищет рантайм по признаку окружения. Признак наследуют дочерние процессы, поэтому рантайм, запущенный из терминала другого рантайма, может определиться неверно. Явное имя надёжнее.

Чтобы подключить новый рантайм, добавь `runtime-config/runtimes/<id>.json` по образцу соседнего файла, впиши id в `manifest.json` и запусти проверки:

```bash
python3 -m unittest discover -s .handoff -p 'test_*.py' -v
```

Каждый поддерживаемый рантайм читает корневой [AGENTS.md](../AGENTS.md). Claude Code приходит к нему через [CLAUDE.md](../CLAUDE.md).

## 3. Что считать доказанным

| Метка | Значение |
|---|---|
| Проверено | Агент наблюдал результат; указаны команда или ресурс, время и фактический итог |
| Не проверено | Команда не выполнялась либо ресурс недоступен; указана причина |
| Частично | Выполнена только часть критерия; явно перечислено, что остаётся |
| Блокировано | Следующее нужное действие невозможно; описаны препятствие и условие продолжения |
| Предложение | Будущая идея, для которой ещё нет разрешения на выполнение |

Успешный локальный тест не подтверждает работу облачного API или всех сценариев `chebu`.
Закрытый issue, статус «Готово» и завершённая реализация фиксируются отдельно, если они расходятся.
Вывод предыдущего агента является подсказкой для проверки, а не новым наблюдением.
В поле «Рантайм» пиши id, который напечатала команда `start`. Модель записывай только при наличии надёжных данных рантайма. Если модель скрыта, пиши `неизвестна`. Модель вспомогательного агента не доказывает модель ведущего.

## 4. Первая сессия

Команда `start` сообщает о первой сессии, когда в клоне нет ни `SESSION.md`, ни архивных снимков. Предыдущего контекста нет, поэтому состояние собирает сам агент.

1. Прочитай [корневой README](../README.md) и [правила учёта задач](../coding-agent-developement/project-tracking.md).
2. Выполни Git-проверки из раздела 6.
3. Спроси ученика о цели сессии, покажи [режимы тьютора](../coding-agent-developement/tutor-modes.md) и вместе с ним выбери режим и тикет.
4. Объясни ученику состояние репозитория и одно следующее действие.

Первая сессия завершается обычным закрытием по разделам 6 и 7. Папку `archive/` создаёт команда `save`.

## 5. Возобновление сессии

1. Прочитай `SESSION.md`, путь к которому напечатала команда `start`. Учитывай время снимка и отмеченную неизвестность.
2. Прочитай текущую задачу ученика и документы, на которые ссылается снимок.
3. Повтори Git-проверки из раздела 6: HEAD, ветка, tracked, untracked, ignored, remotes, теги и worktrees.
4. Сверь фактические файлы и diff с незакоммиченной работой из снимка. Сохрани изменения других участников.
5. Прочитай выбранный issue и карточку Project заново, даже если снимок сообщает «Готово».
6. Сопоставь результаты со снимком и объясни ученику, что актуально, что изменилось и что не проверено.

Неожиданное изменение HEAD, другой worktree или новый запрос ученика требуют пересчитать план.
Следуй текущим ограничениям ученика. Прежнее предложение в снимке не становится разрешением на реализацию.
При отсутствии сети продолжай локальную проверку и назови зависимый блокер.
Тесты повторяй по изменившемуся коду и критерию задачи. Старый успех сам по себе недостаточен.
Локальные проверки не запускают платные API-запросы и установку зависимостей.
Если задача ещё не выбрана, сначала объясни актуальное состояние и варианты.

Режим тьютора продолжается из снимка: команда `start` печатает его, агент называет режим в первом сообщении и повторно о нём не спрашивает. Если снимок режима не содержит, агент показывает [режимы](../coding-agent-developement/tutor-modes.md) и спрашивает один раз.

Возобновление завершено, когда статус объяснён, расхождения учтены и следующий шаг соответствует текущей задаче ученика.

Если `SESSION.md` отсутствует, а архив есть, команда `start` называет последний архивный снимок, и возобновление идёт по нему. Его относительные ссылки отсчитываются от `.handoff/`, а не от `archive/`. Для просмотра с кликабельными ссылками скопируй архив в игнорируемый `.handoff/ARCHIVE-VIEW.md`.

## 6. Закрытие сессии: собрать факты

1. Прочитай последнюю задачу ученика и отдели разрешённую работу от предложений на будущее.
2. Остановись на наблюдаемой границе: законченное действие, понятный частичный результат или конкретный блокер.
3. Сверь итог с текущими файлами и diff. Перечисли результаты со ссылками вместо пересказа истории.
4. Сними Git-состояние командами ниже из корня рабочей копии и запиши время наблюдения в UTC.

```bash
git rev-parse --show-toplevel
git branch --show-current
git rev-parse HEAD
git status --short --branch --untracked-files=all
git diff --stat
git diff --cached --stat
git status --short --ignored
git remote -v
git tag --list
git worktree list --porcelain
```

Полный HEAD сохраняется в метаданных. Пустое имя ветки означает detached HEAD.
Запиши staged, unstaged и untracked отдельно: файл и цель его изменения, включая чужую незавершённую работу.
Ignored-файлы перечисляй по назначению, например локальная `.venv` или состояние `.handoff/`. Содержимое секретов не читай.
Дерево называется чистым только после проверки tracked, untracked и ignored. Присутствие состояния `.handoff/` в ignored не является незакоммиченной правкой проекта.
Сохраняй пути относительно корня. Для соседнего worktree допустим путь `../...`.
Из вывода remotes сохраняй только публичные URL без учётных данных.
Выпуск определяй по тегам и [правилам версий](../VERSIONING.md), отдельно от HEAD текущей сессии. Номер версии в README не доказывает, что HEAD совпадает с релизным тегом.

5. Для каждой проверки запиши точную команду, рабочую папку, время, exit code и краткий результат.
6. Если проверка запускалась раньше, укажи проверенный HEAD или состояние файлов. Успех не переносится на изменившийся код.
7. Команды, которые только предлагаются следующему агенту, пометь «не запускалась» и объясни назначение.
8. Сверь выбранный issue и Project по [правилам учёта задач](../coding-agent-developement/project-tracking.md).

При доступном GitHub прочитай issue целиком, его state и критерии, затем статус карточки Project.
В репозитории два remote. Команда `gh` без ключа `-R` может обратиться к `upstream`, поэтому называй репозиторий явно: `gh issue view 6 -R <owner>/<repo>`.
Сохрани публичные URL, фактические статусы и время просмотра. Запись roadmap эту проверку не заменяет.
При отсутствии доступа отметь «не проверено» или «блокировано» и оставь прежнее значение как исторический снимок.
Если issue выполнен частично или блокирован, перечисли оставшиеся критерии независимо от статуса карточки.
Закрытие сессии само не разрешает закрывать issues, двигать карточки и публиковать изменения. Если текущая задача ученика уже разрешает работу по issue и ведение трекера, записи результатов и смена Status входят в это разрешение.

9. Выбери одно ближайшее действие в текущей задаче: что сделать, где и какой результат подтвердит завершение.
10. Сохрани ограничения ученика, открытые вопросы, блокеры и условия продолжения. Backlog остаётся списком идей.
11. Запиши режим тьютора и заполни раздел «Учебное состояние»: тикет и шаг, пройденные темы, заданные вопросы с итогами, папки песочницы. По этим записям следующий рантайм продолжит обучение с того же места.

Сбор завершён, когда каждый раздел шаблона заполнен фактом либо явным «не проверено», «нет» или «неизвестно». HEAD, успех проверки, URL issue и состояние Project записываются только по наблюдению.

## 7. Закрытие сессии: сохранить снимок

Один назначенный агент пишет снимок. Параллельные участники передают ему сведения и файл сами не заменяют.

1. Скопируй [TEMPLATE.md](TEMPLATE.md) в `.handoff/SESSION.next.md` своей рабочей копии. В основном клоне это папка состояния, в git worktree это его собственная `.handoff/`.
2. Заполни каждое поле наблюдением. Недоступные сведения отметь «неизвестно» или «не проверено» с причиной. Заголовки разделов и строки таблицы метаданных оставь как в шаблоне: по ним скрипт сверяет снимок.
3. Выполни `python3 .handoff/handoff.py save`.
4. Исправляй ошибки, которые назвала команда, и повторяй шаг 3 до успешного завершения.
5. Передай ученику путь снимка, одно следующее действие, существенные непроверенные пункты и команды продолжения, которые напечатала `save`.

Команда `save` сохраняет только снимок, который прошёл проверку. Ту же проверку без сохранения выполняет `python3 .handoff/handoff.py check`.

| Что проверяет `check` | Почему |
|---|---|
| Разделы и поля метаданных совпадают с шаблоном | Следующий агент находит факт на привычном месте |
| Не осталось подсказок шаблона вида `<...>` | Незаполненное поле выглядит как факт |
| Рантайм назван id из `manifest.json` либо `unknown` | По id называется архив и выбирается конфигурация |
| Режим тьютора входит в список шаблона | По id режима следующий агент выбирает правила работы |
| Время снимка записано в UTC | По времени определяется более новый снимок |
| Нет домашних путей, ключей, токенов, адресов почты | Снимок переносится между машинами и рантаймами |
| Относительные ссылки ведут к существующим файлам | Ссылка заменяет пересказ документа |

Затем `save` выполняет запись:

- Отказывается работать, если Git не игнорирует `SESSION.md`. Так состояние не попадёт в публикацию.
- Отказывается заменить более новый снимок более старым. Сначала прочитай существующий `SESSION.md` и перенеси чужие сведения.
- Копирует прежний `SESSION.md` без изменений в `archive/` под именем `YYYYMMDDTHHMMSSffffffZ-<id>.md`. Время в имени соответствует моменту архивирования в UTC, а id называет рантайм прежнего снимка.
- Атомарно переименовывает `SESSION.next.md` в `SESSION.md`.
- Печатает команды, которыми сессию продолжают в каждом рантайме.

Ссылки снимка имеют логическую базу `.handoff/`, и перемещение копии в `archive/` эту базу не меняет. Публичные URL GitHub и относительные пути к файлам проекта допустимы. Личные адреса почты, логины сервисов, абсолютные домашние пути, токены и журналы авторизации в снимок не входят.

Skills зависят от рантайма и машины. Протокол выполняется без них. Если skill помог в сессии, назови его в разделе «Необязательные skills» снимка, а следующий агент возьмёт доступный эквивалент.
